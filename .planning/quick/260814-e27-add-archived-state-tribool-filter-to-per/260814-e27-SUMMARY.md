# Quick Task 260814-e27: Archived filter on personal records — Summary

## What shipped

An `archived` tribool filter — `all` / `archived` / `not_archived` — on both
personal-records endpoints, all the way from SQL to the Discord slash command.

| Surface | Change |
|---|---|
| `libs/sdk/.../completions.py` | New `ArchivedFilter` literal alias, exported |
| `repository/completions_repository.py` | `archived` kwarg on `fetch_user_completions` + `fetch_world_records_per_user` |
| `services/completions_service.py` | Threaded through both service methods |
| `routes/v3/completions.py` | `archived` query param on `GET /completions` and `GET /completions/world-records` |
| `bot/extensions/api_service.py` | `archived` param on both fetch helpers |
| `bot/extensions/completions.py` | `archived` choice on `/user-completions` and `/world-records` |

Default is `all` — byte-identical to pre-change behaviour, asserted by test.

## Notable finding

In **both** queries `rank()` is computed *before* the join to `core.maps`
(`rankable`/`nonrankable` over `latest_per_user_all`; `ranked` over
`latest_per_user_per_map`). So filtering maps cannot corrupt a record's rank on
the maps that remain — the filter selects which maps are listed, not which
competitors count toward a rank. `test_filter_does_not_change_rank` pins this:
a second, faster user is added to the non-archived map, and the target user's
rank of 2 is asserted identical with and without the filter.

The predicate sits on the map rather than post-join so `COUNT(*) OVER()`
(`total_results`, driving pagination) stays consistent with the filtered set.
