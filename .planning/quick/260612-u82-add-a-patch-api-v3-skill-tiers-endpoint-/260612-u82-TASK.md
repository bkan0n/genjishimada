# Quick Task 260612-u82 — Full Specification

Add a `PATCH /api/v3/skill/tiers` endpoint that lets an admin tune the skill **tier percentiles** — the only tunable in the percentile-based tier system added in quick task `260612-pyo`.

This is symmetric with the existing `PATCH /api/v3/skill/config` (which tunes scoring **weights**). It does NOT touch scoring weights, the Ninja→God `skill_rank`, the scorer math, or the boundary-derivation algorithm — it only changes the configured `percentiles` array and re-derives boundaries from the existing snapshot.

## Background (already built in 260612-pyo)

- `skill.tier_config` single row: `boundaries float8[]` (derived cut-points, default `'{}'`), `percentiles float8[]` (the tunable, seeded `[0.50, 0.75, 0.90, 0.97, 0.99, 0.995]`), `computed_at timestamptz`.
- `SkillRepository.compute_tier_boundaries(*, conn=None) -> None` reads `percentiles` from the config row and writes `boundaries` (6 `percentile_cont` cut-points over `skill_score > 0`, or empty under the 20-player population floor); sets `computed_at = now()`. It is invoked inside the single `_do_recompute` path.
- `SkillRepository.fetch_tier_config(*, conn=None) -> dict` returns `{boundaries, percentiles, computed_at}`.
- `SkillService.get_tier_config() -> SkillTiersResponse`.
- `GET /api/v3/skill/tiers` (public read) returns `SkillTiersResponse`.
- `SkillTiersResponse(Struct)`: `boundaries: list[float]`, `percentiles: list[float]`, `computed_at: datetime` in `libs/sdk/src/genjishimada_sdk/skill.py`.
- Existing admin write pattern: `PATCH /api/v3/skill/config` handler `update_config` in `apps/api/routes/v3/skill.py`, gated `opt={"required_scopes": {"skill:admin"}}` (a sentinel scope no normal token holds, so only a superuser passes). Backed by `SkillService.update_weights` → `SkillRepository.update_weights`. Mirror this layering and scope EXACTLY.

## Requirements

### SDK
- Add a request struct (e.g. `SkillTiersUpdateRequest`) to `libs/sdk/src/genjishimada_sdk/skill.py` with `percentiles: list[float]`, full Google docstring, and add it to `__all__` (keep the tuple alphabetically sorted — ruff RUF022).

### Validation (in the service, raising the project's standard HTTP/domain error)
The endpoint MUST reject invalid input with a 400 (use the same error style the codebase uses for skill/config validation; check how `update_config`/`update_weights` validates and mirror it). Rules:
- exactly **6** percentiles (must match the 6 boundary cut-points the tier system expects),
- all strictly between 0 and 1 (`0 < p < 1`),
- **strictly increasing** (each greater than the previous).
On any violation, do NOT persist anything.

### Repository
- Add `SkillRepository.update_percentiles(percentiles: list[float], *, conn: Connection | None = None) -> dict` that `UPDATE skill.tier_config SET percentiles = $1` (bind the float8[] positionally — no string interpolation) and returns the updated row (or fetches it). Keep it minimal and consistent with `update_weights`.

### Service
- Add `SkillService.update_tier_config(percentiles: list[float]) -> SkillTiersResponse`:
  1. validate (above),
  2. persist via `update_percentiles`,
  3. immediately re-derive boundaries from the current snapshot by calling the existing `compute_tier_boundaries` (do NOT re-run the full `recompute_all`/snapshot rebuild — scores are unchanged; only the percentile config changed). Reuse the existing repository method; do not duplicate the boundary SQL.
  4. return the fresh `SkillTiersResponse` (via `fetch_tier_config` / `get_tier_config`).
- Acquire a connection from the pool and pass it to both `update_percentiles` and `compute_tier_boundaries` so the percentile write + boundary re-derivation happen on the same connection (consistent, ideally in one transaction). Follow the existing service connection-acquire pattern.

### Route
- Add `PATCH /tiers` handler `update_tiers` to `SkillController` in `apps/api/routes/v3/skill.py`, gated `opt={"required_scopes": {"skill:admin"}}` (same sentinel as `update_config`), accepting `SkillTiersUpdateRequest`, returning `SkillTiersResponse`. Google docstring; full type annotations.

## Constraints

- Litestar + AsyncPG + msgspec, raw SQL (no ORM), three-layer Controller→Service→Repository.
- No NEW auth scope name beyond the existing `skill:admin` sentinel already used by `update_config`.
- Do NOT modify scoring weights, `skill.weight_config`, the `skill_rank` CASE, the scorer math, or the `compute_tier_boundaries` SQL itself.
- No hardcoded score cutoffs anywhere; percentiles remain the only tunable.

## Acceptance criteria

- `PATCH /api/v3/skill/tiers` with a valid 6-element strictly-increasing percentile array in `(0,1)`: persists the new percentiles, re-derives boundaries, returns the updated `SkillTiersResponse` whose `percentiles` match the request and whose `boundaries`/`computed_at` reflect the recomputation.
- Invalid input (wrong length, out of `(0,1)`, not strictly increasing) → 400, nothing persisted.
- Endpoint requires `skill:admin` (superuser); a normal/anonymous caller is rejected (mirror `update_config`'s auth behavior — confirm how the existing skill tests assert this and follow suit).
- After a successful PATCH, `GET /api/v3/skill/tiers` reflects the new percentiles.
- Scoring weights, `skill_rank`, and `skill_score` are unchanged.
- `just lint-api` passes (ruff + basedpyright strict, 0 errors).
- Skill tests pass with testmon disabled, including a new test for the PATCH happy path, the validation-rejection path, and (matching existing skill-config auth-test style) the scope/auth gate:
  `uv run --env-file .env.local pytest apps/api/tests/integration/test_skill.py apps/api/tests/services/test_skill_service.py -o addopts="" -p no:cacheprovider -q`
