FRONTEND SCOPE (state this explicitly near the top): the web frontend is public read-only display + an admin dashboard. Player time submission and mod verify/reject happen via the DISCORD BOT on the regular completion path — NOT the web frontend. Do NOT document a web submit UI flow.

Use these target sections:

(1) Mental model — Edition vs Cycle vs Category.
  - Category = a difficulty-grouped tournament track with its own reward config (NO per-category cadence anymore).
  - Cycle = one run of a category on one selected map; exactly one `active` cycle per category at a time; status flow `pending → active → finalizing → completed`.
  - Edition = the shared grid-anchored TIMING parent across all categories; status flow `active → awaiting_results → completed`; carries the one shared `started_at`/`ends_at`. Cycles link to an edition internally.
  - Automatic transitions: a pg_cron job runs every minute; at an edition boundary it finalizes cycles, sets the edition to `awaiting_results` (results may be deferred until in-flight verifications drain), starts the next edition at the EXACT grid boundary (`started_at` = previous `ends_at`, never `now()` — the drift fix), and pre-rolls the next pending cycle per category. The frontend learns of transitions by re-polling.
  - `awaiting_results`: edition term ended but final standings deferred pending verification drain; results then publish (or are force-published via `PATCH /publish-results`).

(2) Auth & scopes — `X-API-KEY` header. `tournaments:read` (all GETs), `tournaments:write` (admin mutations), `tournaments:verify` (bot verify/reject only). Superusers bypass. Missing/insufficient scope → 401.

(3) Data models — document ONLY fields that exist now (exact names from the SDK):
  - `TournamentConfigResponse`: blacklist_weeks:int, cadence:"weekly"|"biweekly", anchor_weekday:int (0=Sun..6=Sat), anchor_time:time (wall-clock in anchor_tz), anchor_tz:str (IANA), transitions_paused:bool, debug_cycle_seconds:int|null, created_at, updated_at.
  - `TournamentCategoryResponse`: id, name, difficulties:DifficultyTop[], participation_xp:int, placement_xp:[{place,xp}], streak_xp:[{threshold,xp}], champion_role_id:int|null, is_active:bool, created_at, updated_at. (NO cycle_frequency.)
  - `TournamentEditionResponse`: id:int, started_at:datetime, ends_at:datetime (STORED, not derived), status:"active"|"awaiting_results"|"completed", created_at.
  - `TournamentCycleWithWinnerResponse` (rows of /cycles): id, category_id, map_id, map_code, map_name, map_difficulty:str, status, started_at:datetime|null, ended_at:datetime|null, created_at, winner_name:str|null, winner_user_id:int|null.
  - `TournamentCycleListResponse`: total:int, cycles:[].
  - `TournamentNextCycleResponse`: id, category_id, map_id, map_code, map_name, map_difficulty:str, status (always "pending"), created_at.
  - `TournamentLeaderboardEntryResponse`: rank:int, user_id:int, name:str, time:float(seconds), verified:bool, completion:bool.
  - `TournamentStreakResponse`: user_id, current_streak:int, max_streak:int, last_cycle_id:int|null, updated_at.
  - `TournamentLifecycleResponse`: transitions_paused:bool, debug_cycle_seconds:int|null.
  - Request bodies: `TournamentCategoryCreateRequest` {name, difficulties required; participation_xp=0, placement_xp=[], streak_xp=[], champion_role_id=null — NO cycle_frequency}; `TournamentCategoryPatchRequest` (all optional: name, difficulties, participation_xp, placement_xp, streak_xp, champion_role_id, is_active); `TournamentConfigPatchRequest` (all optional: blacklist_weeks, cadence, anchor_weekday, anchor_time, anchor_tz); `TournamentChooseMapRequest` {map_code}; `TournamentPauseRequest` {paused:bool}; `TournamentDebugCycleLengthRequest` {seconds:int|null}.

(4) Endpoints (base path `/api/v3/tournaments`) split into three groups:
  Public read (scope tournaments:read):
  - GET /config → TournamentConfigResponse
  - GET /categories → TournamentCategoryResponse[]
  - GET /categories/{id} → TournamentCategoryResponse (404)
  - GET /streaks/{user_id} → TournamentStreakResponse (404 = no streak yet)
  - GET /cycles → TournamentCycleListResponse (query: status, category_id, limit 1-100 default 20, offset default 0)
  - GET /cycles/{cycle_id}/leaderboard → TournamentLeaderboardEntryResponse[] (unpaginated, pre-ranked)
  - GET /categories/{id}/next-cycle → TournamentNextCycleResponse (404 category or no pending)
  - GET /editions/active → TournamentEditionResponse (404 if none active)
  Admin dashboard write (scope tournaments:write):
  - POST /categories → 201 (409 name exists)
  - PATCH /categories/{id} → 200 (404; 409 locked or name conflict)
  - DELETE /categories/{id} → 204 (404; 409 locked)
  - PATCH /config → 200 (422 invalid anchor_tz)
  - POST /categories/{id}/select-map → 201 (404; 409 pending exists; 422 no eligible maps)
  - POST /categories/{id}/reroll → 201 (404; 422 no eligible maps) — discards pending, re-randomizes
  - POST /categories/{id}/reroll-active → 201 (404 category/active not found; 422 no eligible maps) — rerolls the LIVE active cycle's map, WIPES its submissions, preserves the edition window
  - PATCH /categories/{id}/next-cycle (body {map_code}) → 200 (404; 422 map not eligible) — explicitly choose pending map
  - POST /bootstrap → 201 (409 active edition exists; 422 a category has no eligible maps) — manually activate the FIRST grid-snapped edition; thereafter rollover is automatic
  - PATCH /publish-results → 204 (409 if no edition awaiting_results) — force-publish results, ignoring in-flight verifications
  - PATCH /pause (body {paused}) → TournamentLifecycleResponse — GLOBAL hiatus; active edition still finishes its term, only the NEXT edition is suppressed
  - PATCH /debug-cycle-length (body {seconds:int|null}) → TournamentLifecycleResponse — DEBUG/TEST ONLY, 403 in production; null clears override
  Discord-bot only — NOT the web dashboard (scope tournaments:verify):
  - PATCH /completions/{tournament_completion_id}/verify → JobStatusResponse (404)
  - PATCH /completions/{tournament_completion_id}/reject → JobStatusResponse (404; 409 already verified — verified is terminal)
  Explicitly state there is NO `POST /cycles/{cycle_id}/submit`. Tournament completions are created server-side when a user submits a normal completion via `POST /api/v3/completions/`; the API auto-detects an active tournament cycle by map code. That path is async/job-based (returns CompletionSubmissionJobResponse {job_status, completion_id}), not a synchronous 201. The web frontend does not submit tournament times.

(5) Frontend flows — describe what the UI renders/calls for each:
  - View active tournament + countdown: GET /editions/active for the shared window, GET /cycles?status=active&category_id={id} (take cycles[0]) for the current map per category. Countdown = edition.ends_at − now() read from the STORED field; NO derivation from started_at + cadence.
  - Leaderboard: GET /cycles/{cycle_id}/leaderboard (already ranked).
  - Archive / past champions: GET /cycles?status=completed (winner_name/winner_user_id per row).
  - Streaks: GET /streaks/{user_id}.
  - Admin dashboard: category CRUD; config (cadence + anchor); map preview/select/reroll/reroll-active/choose; pause; bootstrap; force-publish.

(6) Polling — all writes are synchronous EXCEPT verify/reject and tournament-completion submission, which are async/job-based. Re-poll to learn of automatic transitions. Countdown from the stored ends_at.

(7) Reference values — cycle statuses (pending/active/finalizing/completed), edition statuses (active/awaiting_results/completed), cadence (weekly/biweekly), difficulty tiers (DifficultyTop), ranking rule (verified DESC then time ASC — verified always outranks unverified, fastest wins within a tier; rank precomputed), and the verified vs completion distinction (verified = passed verification, affects ranking tier; completion = counted as a full completion for quest/badge eligibility, distinct from verified). Champion = winner_user_id of a completed cycle (rank 1 at finalization); Discord role transfer is bot-side; category.champion_role_id names the role (may be null).

DROP from the old spec: the §7 ends_at-derivation math, the §8 "gaps" list (gap #1 is now closed by the Edition entity). If useful, mention inline that there is no single "active cycle for category" endpoint — use GET /cycles?status=active&category_id and take cycles[0]. Do not document deprecated SDK structs (TournamentCyclesStartedEvent/TournamentCyclesCompletedEvent) or RabbitMQ event internals — this is a frontend spec.

Keep it shorter and simpler than the original.
