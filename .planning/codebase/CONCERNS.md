# Technical Concerns & Debt

> Generated by gsd-codebase-mapper | 2026-05-29

## Overview

The codebase is architecturally sound with a clean three-layer API design and well-structured domain exception hierarchy. However, there are significant type safety concerns (55+ `# type: ignore[arg-type]` suppressions in service layer alone), a few security gaps (missing file upload validation, no CORS configuration, hardcoded user IDs), and notable bot-side code quality issues (entire files with lint/type-check disabled). The largest technical risk is the git-sourced discord.py dependency pinned to `master`, which can break without warning.

## High Severity

### H1: Pervasive `type: ignore[arg-type]` on Connection Parameters

- **Issue:** 55+ instances of `conn=conn  # type: ignore[arg-type]` across the service layer where `Connection` objects acquired from `pool.acquire()` are passed to repository methods that accept `Connection | None`.
- **Files:** `apps/api/services/maps_service.py`, `apps/api/services/content_service.py`, `apps/api/services/auth_service.py`, `apps/api/services/store_service.py`, `apps/api/services/lootbox_service.py`, `apps/api/services/rank_card_service.py`, `apps/api/services/playtest_service.py`, `apps/api/services/completions_service.py`
- **Impact:** Masks real type errors; the connection returned by `pool.acquire()` is `PoolConnectionProxy` which is compatible with `Connection`, but the suppress annotations make it impossible to catch genuine misuse.
- **Fix approach:** Update `BaseRepository._get_connection()` signature and all repository method signatures to accept `Connection | Pool` (or the `PoolConnectionProxy` type) instead of `Connection | None`, eliminating the need for suppressions. Alternatively, use `typing.cast()` in a single shared helper.

### H2: Missing File Upload Content-Type Validation

- **Issue:** The image upload endpoint at `apps/api/routes/v3/utilities.py:39` reads the full file and passes `data.content_type` directly to S3 without validating that it is an allowed image type. The `_content_type_ext` map in `apps/api/services/image_storage_service.py:18` falls back to `"bin"` for unknown types but does not reject them.
- **Files:** `apps/api/routes/v3/utilities.py`, `apps/api/services/image_storage_service.py`
- **Impact:** Attackers can upload arbitrary file types (HTML, SVG with embedded JS, executables) to the CDN. Since the CDN URL (`cdn.genji.pk`) is trusted, this enables stored XSS or malware distribution.
- **Fix approach:** Add content-type validation in `upload_screenshot()` that rejects any type not in `_content_type_ext`. Also validate file magic bytes, not just the declared content-type header.

### H3: No CORS Configuration

- **Issue:** The Litestar application in `apps/api/app.py` has no `CORSConfig` configured. The API serves a frontend website at `genji.pk`.
- **Files:** `apps/api/app.py`
- **Impact:** Browser-based clients cannot make cross-origin requests to the API, or if a reverse proxy adds permissive CORS headers, there is no application-level control over allowed origins.
- **Fix approach:** Add `CORSConfig` to the Litestar app with explicit `allow_origins` for `genji.pk` and `dev-api.genji.pk`.

### H4: Git-Sourced discord.py Pinned to `master`

- **Issue:** Both `discord-py` and `discord-ext-menus` are installed from git with no pinned commit hash -- just `rev = "master"` and bare default branch respectively.
- **Files:** `apps/bot/pyproject.toml:25-26`
- **Impact:** Any `uv sync` or CI run can pull a breaking change from the discord.py master branch. This has historically caused outages in discord.py-based bots when API-breaking changes land on master.
- **Fix approach:** Pin both dependencies to a specific commit SHA in `pyproject.toml`.

### H5: Hardcoded Discord User IDs for Authorization

- **Issue:** Bot admin commands use hardcoded Discord user IDs for access control: `{681391478605479948, 141372217677053952}`. A hardcoded Discord user ID `<@141372217677053952>` also appears in DLQ alert messages.
- **Files:** `apps/bot/extensions/housekeeping.py:57`, `apps/bot/extensions/rabbit.py:316`
- **Impact:** If a team member leaves or new admins need access, code changes and redeployment are required. The hardcoded mention in DLQ alerts will ping the wrong person if ownership changes.
- **Fix approach:** Move authorized user IDs to the bot's TOML config files (`apps/bot/configs/dev.toml`, `apps/bot/configs/prod.toml`). Use config-driven admin lists.

### H6: Hardcoded Bot User ID in Completions Service

- **Issue:** `BOT_USER_ID = 969632729643753482` is hardcoded at module level in the API service layer.
- **Files:** `apps/api/services/completions_service.py:72`
- **Impact:** If the bot account changes (staging vs production, new bot token), auto-verification and completion rejection will use the wrong user ID. This is a cross-environment bug waiting to happen.
- **Fix approach:** Move to environment variable or configuration. The API already has `APP_ENVIRONMENT` -- use it to select the correct bot user ID.

## Medium Severity

### M1: Entire File Type-Check and Lint Disabled (`tags_paginator.py`)

- **Issue:** `tags_paginator.py` starts with `# type: ignore` and `# ruff: noqa`, disabling all type checking and linting for the entire 326-line file. It is adapted from RoboDanny but has not been modernized.
- **Files:** `apps/bot/extensions/tags/tags_paginator.py` (326 lines)
- **Impact:** Any bugs or regressions in this file will not be caught by CI. Type errors in paginator logic could cause runtime crashes in Discord interactions.
- **Fix approach:** Incrementally type-annotate the file and remove the blanket suppressions. Start by removing `# ruff: noqa` and fixing lint issues, then address type errors.

### M2: f-string Logging in Bot Extensions (Convention Violation)

- **Issue:** 40+ instances of f-string interpolation in log calls across bot extensions, violating the documented convention of using `%s` style formatting.
- **Files:** `apps/bot/extensions/rabbit.py`, `apps/bot/extensions/playtest.py`, `apps/bot/extensions/completions.py`, `apps/bot/extensions/api_service.py`, `apps/bot/extensions/moderator.py`, `apps/bot/extensions/newsfeed.py`, `apps/bot/extensions/xp.py`, `apps/bot/core/genji.py`, `apps/bot/utilities/base.py`, `apps/bot/utilities/maps.py`, `apps/api/services/maps_service.py`, `apps/api/services/auth_service.py`, `apps/api/services/lootbox_service.py`
- **Impact:** f-strings evaluate arguments eagerly even when the log level is disabled, wasting CPU. More importantly, Sentry and log aggregation tools cannot group these messages because they lack structured parameters.
- **Fix approach:** Replace `log.debug(f"Processing {event.code}")` with `log.debug("Processing %s", event.code)` across all affected files.

### M3: No `page_size` Upper Bound Validation

- **Issue:** Multiple paginated endpoints accept `page_size: int = 10` with no maximum limit. The `return_all: bool = False` flag on the maps endpoint bypasses pagination entirely.
- **Files:** `apps/api/routes/v3/maps.py:136`, `apps/api/routes/v3/completions.py:76,202,263,278,306,350`, `apps/api/routes/v3/community.py:62`, `apps/api/routes/v3/newsfeed.py:63`
- **Impact:** A client can request `page_size=1000000` or `return_all=true`, causing the API to load the entire dataset into memory. This is a denial-of-service vector.
- **Fix approach:** Add `le=100` constraint to `page_size` parameters using Litestar's `Parameter` validation. Add scope-based guards for `return_all`.

### M4: Temporary/Legacy Chinese Translation Dicts with `_TEMP` Suffix

- **Issue:** Five large dictionaries with `_TEMP` suffix have been present since creation and show no signs of being temporary. They contain hardcoded Chinese map name translations.
- **Files:** `apps/bot/extensions/map_search.py:29-161` (`CN_TRANSLATIONS_TEMP`, `CN_TRANSLATIONS_FIELDS_TEMP`, `CN_FILTER_TRANSLATIONS_TEMP`, `CN_FILTER_2_TRANSLATIONS_TEMP`, `CN_FILTER_3_TRANSLATION_TEMP`)
- **Impact:** Data maintenance burden -- new Overwatch maps require manual addition. The `_TEMP` naming misleads developers into thinking these will be replaced.
- **Fix approach:** Either move translations to a database/config file, or rename to drop the `_TEMP` suffix to reflect they are permanent.

### M5: `handle_db_exceptions` Decorator Is Legacy / Superseded

- **Issue:** The `handle_db_exceptions` decorator in `apps/api/utilities/errors.py:57` catches raw asyncpg exceptions at the route handler level. The CLAUDE.md documents it as "being superseded by the three-tier exception hierarchy." However it still exists and could be used by mistake.
- **Files:** `apps/api/utilities/errors.py:57-147`
- **Impact:** Two different error handling patterns coexist. New developers may use the decorator instead of the preferred repository-exception-to-service-exception-to-HTTP-exception chain, causing inconsistency.
- **Fix approach:** Audit remaining usages (currently only exported, not actively used in routes). If no routes use it, deprecate with a warning comment or remove entirely.

### M6: Synchronous S3 Upload in Async API

- **Issue:** `ImageStorageService.upload_screenshot()` uses synchronous `boto3` client inside an endpoint marked `sync_to_thread=False`. The `boto3.client.upload_fileobj()` call blocks the event loop.
- **Files:** `apps/api/services/image_storage_service.py:44-66`, `apps/api/routes/v3/utilities.py:36-56`
- **Impact:** During image uploads (up to 25MB), the event loop is blocked, preventing all other requests from being processed. Under concurrent upload load this becomes a bottleneck.
- **Fix approach:** Either set `sync_to_thread=True` on the route handler (Litestar will run it in a thread pool), or switch to an async S3 client like `aioboto3`.

### M7: Short-Lived `aiohttp.ClientSession` Created Per Request

- **Issue:** Both OCR verification and playtest chart generation create a new `aiohttp.ClientSession()` per request via `async with aiohttp.ClientSession() as session`.
- **Files:** `apps/api/services/completions_service.py:312-313`, `apps/api/services/maps_service.py:1339-1340`
- **Impact:** Each new session creates a new TCP connection pool, SSL context, and cookie jar -- then tears them all down. This adds latency and wastes resources. The aiohttp documentation explicitly recommends reusing sessions.
- **Fix approach:** Create a shared `aiohttp.ClientSession` at application startup (e.g., on the Litestar `State` object) and inject it into services.

### M8: Mixed HTTP Clients (aiohttp + httpx)

- **Issue:** The API uses both `aiohttp` (for OCR and plotter calls) and `httpx` (for Resend email API). Both are async HTTP clients with overlapping functionality.
- **Files:** `apps/api/services/completions_service.py` (aiohttp), `apps/api/services/maps_service.py` (aiohttp), `apps/api/events/auth.py` (httpx)
- **Impact:** Two HTTP client libraries to maintain, configure, and monitor. Different error types and timeout semantics.
- **Fix approach:** Standardize on one client. `httpx` is already a declared dependency and is the more modern choice for Litestar apps.

### M9: Zero Bot Test Coverage

- **Issue:** The bot (`apps/bot/`) has no test files. The only test-related file found is `playtest.py` which is not a test file. All 43 Python source files in the bot are untested.
- **Files:** `apps/bot/` (entire directory)
- **Impact:** Bot logic changes (queue consumers, Discord interactions, API service client) cannot be verified without manual testing. Queue consumer bugs may only surface in production via DLQ alerts.
- **Fix approach:** Start with unit tests for pure-logic functions (formatters, parsers, translation dicts) and mock-based tests for queue consumers. The `@queue_consumer` decorator's behavior is testable in isolation.

### M10: Broad `except Exception` Catch in Service Methods

- **Issue:** Multiple service methods in `maps_service.py` use `except Exception as e:` as a catch-all followed by `log.error(f"Unexpected error ...: {e}", exc_info=True); raise`. This pattern appears ~12 times.
- **Files:** `apps/api/services/maps_service.py:544,627,658,680,799,838,899,980,1156,1202,1268`
- **Impact:** These catch-all handlers log and re-raise, adding noise without preventing errors. Worse, they can mask the original traceback if logging fails. The `exc_info=True` with f-string logging is also a convention violation.
- **Fix approach:** Remove the catch-all wrappers. Let exceptions propagate naturally to Litestar's exception handlers, which already log 500s and send to Sentry.

## Low Severity

### L1: `Optional` vs Union Syntax Inconsistency

- **Issue:** `apps/api/utilities/errors.py:23` uses `Optional[dict[str, str]]` while the rest of the codebase uses `str | None` (PEP 604 style).
- **Files:** `apps/api/utilities/errors.py:23`
- **Impact:** Minor style inconsistency. Does not affect runtime.
- **Fix approach:** Replace `Optional[dict[str, str]]` with `dict[str, str] | None`.

### L2: `assert dsn` in Application Factory

- **Issue:** `apps/api/app.py:130` uses `assert dsn` to validate the database DSN. Assertions are stripped in optimized Python (`-O`).
- **Files:** `apps/api/app.py:130`
- **Impact:** If DSN is `None` in production with optimization, the assertion is silently skipped and the app attempts to connect with `None` DSN, causing a confusing error.
- **Fix approach:** Replace with `if not dsn: raise RuntimeError("Database DSN not configured")`.

### L3: `assert isinstance(alert_channel, TextChannel)` in DLQ Processor

- **Issue:** Runtime assertions in the DLQ processor that would silently pass in optimized Python.
- **Files:** `apps/bot/extensions/rabbit.py:318`
- **Impact:** If `alert_channel` is not a `TextChannel`, the assertion is silently skipped and `send()` will fail with an opaque `AttributeError`.
- **Fix approach:** Replace with explicit type check and raise/log if wrong channel type.

### L4: `GENJI_API_KEY` vs `API_KEY` Naming Inconsistency

- **Issue:** The bot uses `GENJI_API_KEY` in `apps/bot/extensions/playtest.py:54` while `apps/bot/extensions/api_service.py:183` uses `API_KEY`. Both reference the bot's API key.
- **Files:** `apps/bot/extensions/playtest.py:54`, `apps/bot/extensions/api_service.py:183`
- **Impact:** Confusion over which env var to set. If only one is configured, the other silently defaults to empty string.
- **Fix approach:** Consolidate to a single env var name (preferably `API_KEY` to match `.env.local.example`).

### L5: Large File Complexity

- **Issue:** Several files exceed 1500 lines, suggesting they may benefit from decomposition.
- **Files:** `apps/bot/extensions/moderator.py` (1994 lines), `apps/api/repository/completions_repository.py` (1991 lines), `apps/api/services/maps_service.py` (1984 lines), `apps/bot/extensions/api_service.py` (1924 lines), `apps/api/repository/maps_repository.py` (1711 lines)
- **Impact:** Large files are harder to navigate, test, and review. High cognitive load for contributors.
- **Fix approach:** Extract logical sub-domains. For example, `maps_service.py` could split guide operations, archive operations, and playtest operations into separate service classes.

### L6: Duplicate `_TriFilter` / `CompletionFilter` / `MedalFilter` Definitions

- **Issue:** `_TriFilter`, `CompletionFilter`, `MedalFilter`, and `PlaytestFilter` type aliases are defined identically in two separate files.
- **Files:** `apps/api/utilities/map_search.py:22-25`, `apps/bot/extensions/api_service.py:139-143`
- **Impact:** If filter values change, both definitions must be updated. These types are not in the shared SDK.
- **Fix approach:** Move to `libs/sdk/src/genjishimada_sdk/maps.py` or a shared types module so both API and bot reference the same definition.

### L7: `email.html` Templates as Inline f-strings

- **Issue:** Email HTML templates are defined as inline f-strings in Python event handlers. No HTML escaping is applied to `event.username`.
- **Files:** `apps/api/events/auth.py:52-58,66-72,80-87`
- **Impact:** If a username contains HTML characters (e.g., `<script>`), the email body could render incorrectly. Low risk since usernames are validated, but defense-in-depth is lacking.
- **Fix approach:** Use an HTML template engine (e.g., Jinja2) or at minimum apply `html.escape()` to interpolated values.

### L8: `RuntimeError("Why is there no guild")` in DLQ Processor

- **Issue:** DLQ processing raises `RuntimeError("Why is there no guild")` if the bot's guild is not found, which is not a helpful error message.
- **Files:** `apps/bot/extensions/rabbit.py:315`
- **Impact:** If the bot disconnects from Discord during DLQ processing, this error will appear in logs without actionable context.
- **Fix approach:** Replace with a descriptive error or gracefully skip the DLQ alert when the guild is unavailable.

### L9: `rapidfuzz` Declared but Not Imported

- **Issue:** `rapidfuzz>=3.12.0` is listed as a dependency but no import of `rapidfuzz` was found in the source code.
- **Files:** `apps/api/pyproject.toml` (dependency declaration)
- **Impact:** Unused dependency adds to install time and attack surface.
- **Fix approach:** Verify whether it is used indirectly (e.g., by another package). If not, remove from dependencies.

### L10: Typo in Docstring

- **Issue:** `apps/api/services/image_storage_service.py:45` says "S3-compatible stroage" (typo for "storage") and "THe image" (typo for "The").
- **Files:** `apps/api/services/image_storage_service.py:45-49`
- **Impact:** Documentation quality only.
- **Fix approach:** Fix the typos.
