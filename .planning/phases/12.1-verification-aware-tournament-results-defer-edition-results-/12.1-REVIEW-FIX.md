### CR-01: `force_publish_results` returns wrong response type / stale-status lie

**Files modified:** `apps/api/services/tournament_service.py`, `apps/api/routes/v3/tournaments.py`, `apps/bot/extensions/api_service.py`
**Commit:** 22e919e
**Applied fix:** Adopted option (b) — the semantically cleanest. The deferred-publish design delivers the real result asynchronously via the `edition_results` outbox event, so there is no useful synchronous body. Changed `TournamentService.force_publish_results` to return `None` (dropped the stale pre-flip `msgspec.convert({**edition, "status": "completed"}, ...)`), the route to `status_code=HTTP_204_NO_CONTENT` returning `Response[None]` (mirroring the existing `delete_category` 204 pattern), and the bot's `force_publish_tournament_results` to `Response[None]` calling `self._request(r)` with no `response_model` (the bot already ignores the return value — it is fire-and-forget at the call site). This removes the route/bot shape mismatch that would have raised `msgspec.ValidationError` at runtime.

### CR-02: Drain state machine — start-only publish/mark ordering not transactionally atomic

**Files modified:** `apps/api/services/tournament_outbox_service.py`
**Commit:** cdbd6e1
**Applied fix:** In the `not start_announced and inflight > 0` start-only branch, moved `mark_edition_start_announced` to run BEFORE `publish_message`. `publish_message` opens its own RabbitMQ channel and does not join the caller's `conn` transaction; if it succeeded before the mark and the mark then raised, the transaction would roll back `start_announced` and the next tick would re-publish the start-only rollover with a fresh `public.jobs` UUID (new `message_id`), defeating the bot's idempotency claim and double-announcing the start. Marking first makes the pair atomic: a publish failure after the mark rolls the mark back too. (The CR-02 finding contained extensive self-correcting analysis; the actionable Fix in the **Fix:** section was this ordering swap, which was verified against the source.)
**Note:** requires human verification — transactional ordering / partial-failure semantics.

### CR-03: `_on_edition_results` posts a card even when `event.results` is empty

**Files modified:** `apps/bot/extensions/tournaments.py`
**Commit:** cc4778f
**Applied fix:** Added an early-exit guard `if not event.results:` at the top of `_on_edition_results` (after the debug log), mirroring the defensive guard in `_on_edition_rollover`. An all-rejected / no-submissions edition drains with an empty results list; without the guard the handler unconditionally built and sent a header-only "## Results" card (lines 517-520 run before the `for entry in event.results` loop). Bailing before any champion-role transfer or post means nothing is announced for a zero-results edition. With the guard, the downstream results-section build is reached only when `event.results` is non-empty, so the existing unconditional header is correct.

### WR-01: `_set_verified` TOCTOU window publishes a fresh event on an already-target row

**Files modified:** `apps/api/services/tournament_service.py`
**Commit:** a0607af
**Applied fix:** In the `if updated is None:` block, after re-fetching `current`, added a check: if `current["status"]` already equals the target status (`"verified"` for verify, `"rejected"` for reject), short-circuit via `_noop_verdict_job(...)` instead of falling through to publish a fresh `TournamentVerificationChangedEvent`. A concurrent verdict that landed in the TOCTOU window already granted XP and published; a second publish would ride a new `public.jobs` UUID (new `message_id`) and could be processed twice by the bot. This mirrors the existing already-verified no-op guard at the top of the method.
**Note:** requires human verification — concurrency / idempotency semantics.

### WR-02: `fetch_edition_child_cycles` returns all child cycles regardless of status

**Files modified:** `apps/api/repository/tournaments_repository.py`
**Commit:** 55e7572
**Applied fix:** Added `AND status = 'finalizing'` to the query so results computation only sees the cycles the cron just stopped, not any cycle a prior partial run already flipped to `completed`. Both call sites (`_write_drained_results_row` and the combined-rollover branch) run while the edition is `awaiting_results`, at which point its child cycles are `finalizing` (and only flipped to `completed` by the subsequent `complete_edition` call). Re-including completed cycles would insert a second `edition_results` pending_transition row (no UNIQUE constraint on that table), causing the outbox to drain — and re-grant — the edition twice. Updated the docstring accordingly.
**Note:** requires human verification — depends on the invariant that child cycles are always `finalizing` at call time.

### WR-03: Migration backfill conservatism can wedge an in-flight edition

### WR-05: `count_inflight_verifications` does not filter by cycle status

### WR-04: `check_active_cycle_for_category` does not include `'pending'` cycle status

**File:** `apps/api/repository/tournaments_repository.py:299-307` / `apps/api/services/tournament_service.py:244-265`
**Reason:** skipped — proposed fix contradicts an existing intentional test contract and is out of phase scope. The suggested change (add `'pending'` to `WHERE ... status IN ('active', 'finalizing')`) would break the existing green test `TestCheckActiveCycleForCategory::test_no_active_cycle_returns_none` (`apps/api/tests/repository/tournaments/test_tournaments_repository.py:142-149`), which deliberately creates a `status="pending"` cycle and asserts the result is `None`. This encodes the contract that a pre-rolled pending cycle does NOT lock a category. The method is shared by both `update_category` and `delete_category`, so the change would alter behavior well beyond the `delete_category` path the finding describes. The REVIEW.md text itself classifies this as "a pre-existing gap not introduced by Phase 12.1." Applying it would regress an established test and expand scope, so it is left for a deliberate decision outside this fix pass.
**Original issue:** `check_active_cycle_for_category` checks `status IN ('active', 'finalizing')` but not `'pending'`; a category with only a pending cycle can be deleted, relying on unverified FK cascade behavior.
