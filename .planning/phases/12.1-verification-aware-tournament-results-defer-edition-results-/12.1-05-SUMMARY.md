# Phase 12.1 Plan 05: Bot deferred-results handler + force-publish command Summary

**The bot-side completion of the verification-aware flow: a new `_on_edition_results` consumer posts the deferred results as a SEPARATE Components-V2 card and performs the HELD champion-role transfer (D-04/D-05); `_on_edition_rollover` renders a "Results pending verification…" placeholder when `results_pending=True` (empty results → previous champion keeps the role, D-01/D-05); and a mod-gated `/tournament-publish-results` command (authoritative bot-side `is_mod` gate + confirmation) calls Plan 04's force-publish route via a new `api_service` method (D-03) — bot never touches Postgres.**

## Accomplishments
- **`_on_edition_results` handler (D-04/D-05):** registered with `@queue_consumer("api.tournament.results", struct_type=TournamentEditionResultsEvent, idempotent=True)`, mirroring `_on_edition_rollover`. Transfers the HELD champion role FIRST per result entry (reuses `_transfer_champion_role` verbatim — strip-all-then-grant, staggered, guild-leave-safe, vacant-on-None-winner), then posts ONE results card LAST as a NEW separate announcement (D-04 — no edit-in-place, no stored message ids). An empty/all-rejected edition posts a no-winner card and transfers nothing.
- **Results-pending placeholder (D-01/D-05):** `_on_edition_rollover` renders `## 🏅 Results / Results pending verification…` in place of the results section when `event.results_pending` is True. The transfer loop naturally skips (empty `results`), so the previous champion KEEPS the role through the pending window; the start section renders on time. The empty-event early-return guard was extended so a placeholder-only event (hiatus + pending, possibly no started section) still posts.
- **`/tournament-publish-results` command (D-03):** added to `TournamentRerollCog`, copying the `/tournament-reroll` pattern exactly — `@app_commands.default_permissions(manage_guild=True)` (UI hint), defer ephemeral, then the AUTHORITATIVE bot-side `is_mod` (mod or sensei) gate raising `UserFacingError` before any API call (T-12.1-14). A `ConfirmationView` gate guards the abandon (force-publish drops still-pending runs); on confirm it calls `force_publish_tournament_results()`.
- **`api_service.force_publish_tournament_results` (D-03):** `PATCH /tournaments/publish-results` → `JobStatusResponse`, modeled on `verify_tournament_completion`; the bot reaches the DB only through this HTTP call.
- **Mention-injection mitigation (T-12.1-15):** the deferred results card reuses the rollover card's pattern verbatim — winners referenced ONLY by numeric `<@id>`, the free-text standings `name` never in a mention, ping inside a `ui.TextDisplay`, `AllowedMentions(users=allow-list, everyone=False, roles=False)`.

## Decisions Made
- **Placeholder placement + guard:** the placeholder renders where the results section would; the `not results and not started` early-return was widened with `and not results_pending` so a pending-but-no-start event still posts the placeholder.
- **Edition-scoped force-publish:** `force_publish_tournament_results()` takes no id (PATCH `/tournaments/publish-results`), matching Plan 04's single-`awaiting_results`-edition route.
- **Confirmation gate:** force-publish abandons still-pending runs (irreversible), so a `ConfirmationView` gates it (cancel/timeout never reaches the API); this also reinforces the T-12.1-14 "API not called" assertion.
