# Phase 12.1 Plan 04: Poller drain state machine + force-publish Summary

**Moves results computation + reward grants OUT of pg_cron INTO the outbox poller (the heart of the phase): `process_awaiting_results_editions` implements the D-07 three-branch drain state machine inside the existing publish-before-mark transaction, deferred results ride an `edition_results` outbox row (at-least-once preserved), the champion role is held through the pending window via empty `results`, and an admin force-publish escape hatch (D-03) reuses the same drained path ignoring pending — clearing the last 3 inherited `test_edition_transitions.py` failures so the full suite is green.**

## Accomplishments
- **Poller drain state machine (D-01/D-02/D-05/D-07):** `process_awaiting_results_editions` runs INSIDE the existing `async with pool.acquire() as conn, conn.transaction()` block before the outbox drain. Per `awaiting_results` edition (locked `FOR UPDATE SKIP LOCKED`, `ends_at ASC`) it counts in-flight verifications and branches:
  - first tick, pending == 0 -> compute results from `fetch_leaderboard`, grant XP, publish ONE combined `TournamentRolloverEvent(results_pending=False)`, flip edition + cycles -> `completed`
  - first tick, pending > 0 -> publish a start-only `TournamentRolloverEvent(results_pending=True)` (empty `results` so the bot holds the champion role, D-05), set `start_announced`, NO grants, stay `awaiting_results`
  - later tick, drained -> write an `edition_results` outbox row (the SAME loop drains+publishes+grants it next tick at `tournament:results:{edition_id}`), flip -> `completed`
- **Grant-inside-transaction invariant preserved:** the grant loop (`award_cycle_end` + `_reset_non_participant_streaks`) is reused VERBATIM inside the transaction; the deferred results grant runs exactly once, when the row drains (no double-grant). Module docstring 21-38 intact.
- **Deferred results as an outbox row (Pitfall 3):** `_write_drained_results_row` writes the `edition_results` row + completes; the existing publish-before-mark machinery re-publishes after a crash rather than dropping the announcement.
- **Force-publish (D-03):** `TournamentService.force_publish_results` reuses the shared `_write_drained_results_row` IGNORING `count_inflight_verifications`; abandoned (still-pending) runs are LEFT `pending` (audit trail, Open Q2). PATCH `/api/v3/tournaments/publish-results` requires `tournaments:write` and translates `NoAwaitingResultsEditionError` -> 409.
- **Inherited failures cleared:** rewrote the 3 `test_edition_transitions.py` tests (`TestDrift`, `TestSingleEdition`, `TestHiatus`) to the poller-owns-results model (cron stops at `awaiting_results`/`finalizing`, writes no outbox row). Full suite: **1831 passed, 2 skipped, 2 xfailed, 0 failures**.

## Decisions Made
- **Grant on the drain, not in the helper:** `_write_drained_results_row` does NOT grant — it writes the `edition_results` row and completes; the SAME poll loop grants when it drains that row (mirrors `edition_rollover`). Granting in the helper too would double-grant in one tick. This keeps grant + publish + mark in one transaction (docstring 21-38).
- **CHECK constraint extension in 0025:** the `edition_results` row write was rejected by the 0024-era `pending_transitions_event_type_check`. Extending the CHECK is core to this plan's deliverable, so it was added to migration 0025 (Rule 3 blocking).
- **Service test relocation:** `tests/services/conftest.py` makes `setup_test_db` a no-op, so `tournaments.*` does not exist in the services test DB. The real-DB force-publish service tests were moved to the integration suite (migrated DB) while still exercising `TournamentService` directly.
- **Single-edition force-publish:** force-publish targets the oldest `awaiting_results` edition (no id param), matching the poller's stacked-edition ordering.
