<objective>
The heart of the phase: move results computation + reward grants OUT of pg_cron INTO the existing outbox
poller, and add the admin force-publish escape hatch. The poller gains `process_awaiting_results_editions`
inside the same publish-before-mark transaction, implementing the D-07 three-branch drain state machine
(D-01 four cases), reusing `fetch_leaderboard` + `award_cycle_end` + `_reset_non_participant_streaks`
VERBATIM. Deferred results are written as an `edition_results` outbox row so the existing at-least-once
machinery drains them (Pitfall 3). Force-publish (D-03) reuses the same drain branch ignoring pending runs.

Purpose: This makes results verification-aware. Pending runs no longer get excluded permanently —
the poller waits for drain (D-02, no time cap), holds the champion role through the pending window (D-05,
naturally: deferred results carry empty `results` so the bot skips the transfer), and the combined
no-pending message is preserved for the common case.
Output: poller drain state machine, the deferred-results outbox row write, force-publish service + route,
and integration/poller/service tests covering all three branches + force-publish + stacked/empty editions.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bot/admin (API key + tournaments:write) → PATCH publish-results → service → DB + RabbitMQ | force-publish abandons pending runs, grants placement/streak XP, and triggers the champion-role transfer — a privileged, side-effectful operation |
| poller (own DB connection) → DB + RabbitMQ | the poller computes results, grants XP, and publishes events; a crash or re-delivery must not double-grant or double-transfer |
| API → RabbitMQ → bot | rollover/results events drive XP grants and the champion role; idempotency must prevent duplicates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12.1-09 | EoP | PATCH publish-results | mitigate | Route requires `tournaments:write` scope (V4); scope-guard test asserts a non-superuser read-only token gets 401/403. Bot-side mod gate (authoritative) is added in Plan 05. |
| T-12.1-10 | Tampering (double-grant) | poller + force-publish XP grants | mitigate | `award_cycle_end` is replay-safe via the `UNIQUE(cycle_id,user_id,reason)` ledger; grants stay INSIDE the outbox transaction (docstring 21-38). Poller-rerun test asserts no duplicate grants. |
| T-12.1-11 | Tampering (double-transfer/double-announce) | rollover + results events | mitigate | Idempotency keys `tournament:rollover:{edition_id}` + `tournament:results:{edition_id}` + bot `@queue_consumer(idempotent=True)` (Plan 05) dedupe; a re-delivered message cannot double-transfer the champion role. |
| T-12.1-12 | Tampering (mis-rank/mis-reward) | drain-branch results computation | mitigate | Results computed AFTER drain from `fetch_leaderboard` where only `status='verified'` ranks above pending/rejected; force-publish leaves abandoned runs `pending` so they are excluded — no mis-rank path. |

| T-12.1-SC | Tampering | npm/pip/cargo installs | accept | No package installs (RESEARCH: nothing to install). |
