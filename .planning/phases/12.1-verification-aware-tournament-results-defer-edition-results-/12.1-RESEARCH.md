# Phase 12.1: Verification-aware tournament results - Research

**Researched:** 2026-06-01
**Domain:** PostgreSQL state machine + transactional outbox poller (asyncpg/Litestar) + discord.py CV2 announcement; tri-state verification model
**Confidence:** HIGH (entirely internal codebase; every claim traced to a real line range in this repo)

## Summary

This is a self-contained refactor of an existing, fully-shipped subsystem (Phase 12's combined tournament rollover). The entire "standard stack" is the project's own established machinery: PL/pgSQL pg_cron functions, a `tournaments.pending_transitions` transactional outbox, the `tournament_outbox_poller` lifespan loop, the `TournamentRewardService` grant path, msgspec SDK structs, and a discord.py Components-V2 (LayoutView) announcement card. No new external dependencies are introduced — there is **nothing to install** and therefore no package-legitimacy audit is required. The research effort is entirely about correctly relocating responsibility (cron → poller), extending the state machine (`awaiting_results` edition status + tri-state completion verification), and adding one new SDK event + one new bot handler + one admin command.

The core bug is precisely understood from the code: `process_edition_transitions()` (migration 0024, lines 226-305) snapshots each child cycle's leaderboard via an inline `RANK()` CTE **at the instant pg_cron fires** and freezes it into the `edition_rollover` outbox payload. A run still `verified = FALSE` (whether genuinely pending review or already rejected) sorts below verified runs and is excluded from placement XP and the champion-role transfer — and once published the results are final. The fix is exactly the four moves the CONTEXT locks: (D-06) cron becomes a timing-only status flip to a new `awaiting_results` edition status; (D-07) the poller counts in-flight verifications and computes results only when the queue drains; (D-08) a tri-state verification column makes "drained" detectable (today reject is indistinguishable from pending — both `verified = FALSE`); (D-09) a new results-only SDK event carries the deferred results.

**Primary recommendation:** Implement the tri-state as a **`status` enum column (`pending`/`verified`/`rejected`)** on `tournaments.completions` with a generated/synchronized `verified boolean` kept for backward-compat ranking (or rewrite the two ranking CTEs to derive `verified` from `status='verified'`). Drive results from a new repository method `count_inflight_verifications(edition_id)` that counts child-cycle completions with `status='pending'`. Reuse `fetch_leaderboard` + `award_cycle_end` + `_reset_non_participant_streaks` **verbatim** in the poller — they already operate on freshly-fetched data and per-cycle `TournamentCycleCompletedEvent` shapes. Add `TournamentEditionResultsEvent` on `api.tournament.results` (idempotency `tournament:results:{edition_id}`), keep the no-pending combined case on the existing `TournamentRolloverEvent` (now carrying a `results_pending: bool`), and add a `_on_edition_results` bot handler that runs the held champion transfer + posts a fresh card. Force-publish is a new `tournaments:write` PATCH route + a `/tournament publish-results` mod-gated bot command.

### Pattern 1: pg_cron becomes a pure status flip (D-06)
**What:** Strip the entire results-computation block (0024 lines 226-305: the `best_per_user`/`ranked` CTE, `v_standings`/`v_winner` accumulation, `v_results`) AND the outbox `INSERT` (lines 353-365) out of `process_edition_transitions()`. Keep: the advisory lock (197), config read (202), period computation (206-211), due-edition detection (214-218), the child `UPDATE ... status='finalizing'` (235) — but **stop** at `status='finalizing'` (do NOT also flip to `completed` at line 294-296), the edition flip becomes `active → awaiting_results` (not `completed`), and the N+1 creation block (313-350) stays intact.
**When to use:** This is the rewrite the migration ships.
**Critical:** The cron still flips child cycles to `finalizing` (stops new submissions — the submit guard rejects non-`active` status). The poller later flips both the edition and its cycles to `completed` when results publish.

### Pattern 2: Poller-owned drain state machine (D-07)
**What:** `publish_pending_transitions` gains a second responsibility alongside draining outbox rows. The cleanest structure: a new method (e.g. `process_awaiting_results_editions(conn)`) called inside the SAME `async with pool.acquire() as conn, conn.transaction():` block (lines 152). It queries editions in `awaiting_results`, and per the three branches in the diagram, computes results in Python and either emits `TournamentRolloverEvent` or `TournamentEditionResultsEvent`.
**Key reuse:** The results computation produces a `list[TournamentCycleCompletedEvent]` — the exact same shape `event.results` already holds (the existing reward loop at lines 168-171 iterates this). So the grant path is reused verbatim.

### Pattern 3: "start announced" disambiguation (Claude's Discretion #3)
**What:** The poller must distinguish *first tick (start not yet announced)* from *later tick (results still owed)*.
**Recommendation:** Add a boolean marker on the edition row, e.g. `start_announced boolean NOT NULL DEFAULT FALSE` (or a richer `results_state` enum). Deriving from outbox/announcement records is fragile (outbox rows are deleted on wipe; there is no persisted "announcement sent" record). A column on `tournaments.editions` is the same pattern as `status` and is queryable in one `SELECT`. The first tick with `inflight > 0` sets `start_announced = TRUE`; later ticks see it TRUE and know only results are owed. Combined no-pending case never needs the marker (it goes straight to `completed`).
**Confidence:** MEDIUM — a `results_state` enum (`none`/`start_announced`/`published`) folded onto the edition is an equally valid shape; planner should pick based on how the frontend wants to read it (see frontend spec note below).

### Pattern 4: Reuse `fetch_leaderboard` for poller-side computation (Claude's Discretion #4) — CONFIRMED
**What:** Today the cron computes standings inline (0024 lines 239-292). The poller instead calls the existing `fetch_leaderboard(cycle_id, conn=conn)` (`tournaments_repository.py:1555-1603`) per child cycle and builds the `TournamentCycleCompletedEvent` itself.
**Traced signatures (exact):**
- `fetch_leaderboard(self, cycle_id: int, *, conn) -> list[dict]` — returns dicts with keys `rank, user_id, name, time (float), verified, completion`. These keys are byte-identical to `TournamentLeaderboardEntryResponse` (SDK lines 405-422), so `msgspec.convert(row, TournamentLeaderboardEntryResponse)` works directly (as `get_leaderboard` already does, service line 985).
- Winner = the `rank == 1` row. The CTE's `RANK() OVER (ORDER BY verified DESC, time ASC, inserted_at ASC, user_id ASC)` is **identical** between `fetch_leaderboard` (lines 1590-1592) and the cron (lines 256-258), so winner selection matches. Pick the rank-1 row with the lowest `inserted_at`/`user_id` (the leaderboard already returns them in that order, so `standings[0]` when `rank==1`).
- `award_cycle_end(self, event: TournamentCycleCompletedEvent, *, conn) -> list[XpGrantEvent]` (`tournament_reward_service.py:179`) — already consumes the per-cycle event shape. Feed it the freshly-built event. **No change needed.**
- `_reset_non_participant_streaks(repository, event, *, conn)` (`tournament_outbox_service.py:195`) — takes the same per-cycle event. **No change needed.**
**Confirmation:** YES — reuse verbatim. The poller builds `TournamentCycleCompletedEvent(cycle_id, category_id, standings=[...], winner_user_id=...)` from a fresh `fetch_leaderboard` call, then runs the existing grant loop. The only difference from today is the *source* of the entries (live query vs. frozen snapshot).
**IMPORTANT — tri-state ranking:** When results are computed AFTER drain, all `pending` rows are gone (every completion is `verified` or `rejected`). `fetch_leaderboard` must rank `verified` above both `pending` and `rejected`. See Pattern 5 for the SQL change.

### Pattern 5: Tri-state on `tournaments.completions` (D-08, Claude's Discretion #1) — RECOMMENDATION
**Recommended representation:** a `status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','verified','rejected'))` column.

| Option | Drain-detection | Ranking | Existing code impact | Verdict |
|--------|----------------|---------|----------------------|---------|
| **`status` enum (RECOMMENDED)** | `COUNT(*) WHERE status='pending'` — exact | `verified DESC` becomes `(status='verified') DESC` | verify/reject set `status`; `verified` bool either dropped or kept as a generated column | **Pick this** — single source of truth, naturally extensible, matches frontend's likely needs |
| `rejected boolean` alongside `verified` | `COUNT(*) WHERE verified=FALSE AND rejected=FALSE` | unchanged (`verified DESC`) | smallest diff; verify sets `verified`, reject sets `rejected` | Viable but two booleans can drift into the illegal `(verified=TRUE, rejected=TRUE)` state — needs a CHECK guard `NOT (verified AND rejected)` |
| per-cycle in-flight counter | counter read | unchanged | counter must be transactionally maintained on every submit/verify/reject — easy to desync | **Reject** — denormalized counter is the classic drift bug |

**Why `status` enum:** It is the only option that cannot represent an illegal state, it makes the drain query trivial (`WHERE status='pending'`), and it cleanly answers the frontend's "is this run pending?" question. The cost is touching the two ranking CTEs (`fetch_leaderboard` 1584/1591/1600 and the cron — but the cron's ranking block is being deleted anyway per D-06).

**Backward-compat for ranking:** Two equally valid sub-options:
1. **Keep `verified boolean` as a GENERATED column:** `verified boolean GENERATED ALWAYS AS (status = 'verified') STORED`. Every existing `verified DESC` / `verified` read keeps working unchanged; only writes move to `status`. (Note: a generated column cannot be in the same row's `RETURNING` of an UPDATE that also sets it — verify this against `set_tournament_verified`'s `RETURNING`; it returns `id, cycle_id, user_id, time` only, so it's fine. But `create_tournament_completion` does `RETURNING *` which will include the generated column — that is allowed for generated columns on read.)
2. **Drop `verified`, rewrite the CTEs** to `ORDER BY (status='verified') DESC, time ASC, ...`. Cleaner long-term but a larger blast radius (`TournamentLeaderboardEntryResponse.verified`, `TournamentCompletionResponse.verified`, every test asserting `verified`, the frontend spec's `verified` field).

**Recommendation:** Option 1 (generated `verified` column) for this phase — it preserves the entire ranking surface, all SDK `verified` fields, and the frontend contract with zero ranking-code churn, while making `status` the write-side source of truth. Migration data backfill: `UPDATE tournaments.completions SET status = CASE WHEN verified THEN 'verified' ELSE 'pending' END` BEFORE adding the generated column (you cannot have both a plain `verified` and a generated `verified` — so the migration must: add `status`, backfill, drop old `verified`, re-add `verified` as generated). Sequence this carefully (see Migration Sequencing pitfall).

**Migration number:** **`0025_verification_aware_tournament_results.sql`** (next sequential after 0024 — confirmed `0024` is the highest, `ls apps/api/migrations/`).

### Pattern 6: New results-only event + `results_pending` flag (D-09, Claude's Discretion #2) — RECOMMENDATION
- **`TournamentEditionResultsEvent`** (new struct): fields `edition_id: int`, `results: list[TournamentCycleCompletedEvent]`. Routing `api.tournament.results`, idempotency `tournament:results:{edition_id}`. Add to SDK `__all__`.
- **`TournamentRolloverEvent`** gains `results_pending: bool` (default `False` for back-compat). When `results_pending=True`, `results` is empty (the start-only deferred case). When `results_pending=False`, behaves exactly as today (combined results + started).
- **No-pending combined case keeps `TournamentRolloverEvent` carrying results** (recommended): least disruption to the existing `_on_edition_rollover` handler, which already renders results + started conditionally. The new results event is used ONLY for the deferred (drain-later) path. This keeps "combined" semantics for the common case and avoids forcing the bot to correlate two messages in the normal flow.
- **Outbox routing:** `_EVENT_ROUTING` (`tournament_outbox_service.py:68`) gains `"edition_results": ("api.tournament.results", TournamentEditionResultsEvent)`. But note: in the poller-computes model the poller no longer reads an outbox ROW for these — it computes and publishes inline. The existing `edition_rollover` outbox rows (written by old code / any in-flight at deploy) still drain through `_build_event`. **Decision for planner:** whether the poller writes a transient outbox row for the deferred results (to preserve at-least-once replay) or publishes directly inside the transaction with publish-before-mark semantics. See Pitfall "Outbox vs. direct publish" below — strongly recommend writing an outbox row so the existing at-least-once + idempotency guarantees are preserved unchanged.

### Pattern 7: Held champion role (D-05)
**What:** During the pending window, `_on_edition_rollover` (when `results_pending=True`) renders the start section + "results pending" placeholder but **does NOT call `_transfer_champion_role`** (it only transfers `if event.results`, lines 359-362 — with empty results it naturally skips). The transfer happens later in `_on_edition_results`, which calls `_transfer_champion_role(entry, category)` per result entry (the existing strip-all-then-grant method, lines 497-569, is reused verbatim). The previous champion keeps the role automatically because nothing strips it until the deferred results land.

### Pattern 8: Force-publish (D-03, Claude's Discretion #5) — RECOMMENDATION
**API route:** `PATCH /api/v3/content/.../editions/{edition_id:int}/publish-results` OR scoped to "the edition currently `awaiting_results`" with no id param (recommend the latter — there is normally one). `opt={"required_scopes": {"tournaments:write"}}`. Service method `force_publish_results(edition_id | None)` runs the same drain-branch the poller uses, **ignoring remaining `pending` rows** (D-03), marking remaining `pending` completions as abandoned (leave them `pending` or transition to `rejected` — recommend leaving `pending` so the audit trail shows they were never reviewed; the leaderboard already excludes them since only `verified` runs rank). Flips edition → `completed`, emits the results event.
**No-op/error path:** force-publish when no `awaiting_results` edition exists → `409`/`404` with a clear message (mirror `bootstrap`'s `CycleAlreadyLiveError → 409` pattern, route lines 511-517).
**Bot command:** `/tournament publish-results` as a flat mod-gated command — follow the **exact `/tournament-reroll` pattern** (lines 744-803): `@app_commands.default_permissions(manage_guild=True)` as UI hint, but the AUTHORITATIVE gate is the bot-side `is_mod` role check (`itx.user.get_role(mod) or get_role(sensei)`, lines 780-787) because the bot's single API key cannot distinguish callers. Add a confirmation step (the bot already uses confirmation views elsewhere — planner to confirm a `ConfirmationView` exists; if not, a simple two-step button). Defer ephemeral, call a new `api_service.force_publish_tournament_results()` method (model on `verify_tournament_completion` at `api_service.py:1093`).

### Anti-Patterns to Avoid
- **Computing results in the cron "just for the no-pending case."** D-06 is absolute: cron NEVER computes outcomes. Even the no-pending combined case is computed by the poller's first tick (D-07 bullet 1). The ~10s latency is already the status quo (cron writes a row the poller publishes).
- **Editing the placeholder message in place / storing message IDs.** D-04 forbids this — the deferred results are a NEW message; the bot stores nothing.
- **Moving grants out of the outbox transaction.** The module docstring (lines 21-38) is an explicit, load-bearing invariant: grant + publish + mark are ONE transaction so a crash re-polls the whole unit; the XP ledger makes re-grants idempotent. Preserve this for the deferred-results path too.
- **A time-based grace window.** Explicitly rejected (D-02). Drain-only.

## Common Pitfalls

### Pitfall 1: Migration column-swap ordering (generated `verified`)
**What goes wrong:** You cannot `ADD COLUMN status` + backfill from `verified` AND simultaneously redefine `verified` as `GENERATED ALWAYS AS (status='verified')` in the wrong order — Postgres rejects a generated column whose expression references a column being dropped, and a plain + generated `verified` cannot coexist.
**How to avoid:** Ordered DDL inside one `BEGIN;/COMMIT;`: (1) `ADD COLUMN status text ... DEFAULT 'pending'`; (2) `UPDATE ... SET status = CASE WHEN verified THEN 'verified' ELSE 'pending' END`; (3) `ALTER ... DROP COLUMN verified`; (4) `ALTER ... ADD COLUMN verified boolean GENERATED ALWAYS AS (status='verified') STORED`; (5) recreate the `idx_tournament_completions_ranking` index (dropping `verified` drops the index that referenced it). Migration test must assert the ranking index exists post-migration.
**Warning signs:** `cannot drop column verified because other objects depend on it` (the ranking index) — drop the index first.

### Pitfall 2: payload/struct key drift surfaces as `msgspec.ValidationError`
**What goes wrong:** The outbox `jsonb_build_object` keys must be byte-identical to the SDK struct fields or `msgspec.convert` raises and the row stays unpublished (documented at outbox 64-67, 98-101). Adding `results_pending` to `TournamentRolloverEvent` without a default breaks every old-shape payload.
**How to avoid:** `results_pending: bool = False` (default) so old payloads convert. For the new `TournamentEditionResultsEvent`, if the poller publishes inline (not via an outbox row) there is no jsonb round-trip — but if it writes an outbox row, the row's payload keys must match exactly.
**Warning signs:** A poller log showing repeated unpublished rows; a `msgspec.ValidationError` in Sentry.

### Pitfall 3: Outbox-vs-direct-publish for deferred results
**What goes wrong:** If the poller computes results and publishes directly (not via an outbox row), a crash between the grant-commit and the publish loses the at-least-once guarantee that the existing design provides via the row.
**How to avoid (recommended):** Have the poller, when it detects drain, **write an `edition_results` outbox row** (status flip to `completed` + row insert in one txn), then let the SAME loop drain that row on the next tick via the existing publish-before-mark path. This reuses the proven crash-safety + idempotency machinery unchanged. The grants run when the row is drained (same as today). Alternatively, compute+grant+publish+flip all in one transaction with publish-before-flip — but that re-implements the outbox semantics. Planner to choose; outbox-row reuse is lower-risk.
**Warning signs:** Lost results announcement after a poller crash mid-drain.

### Pitfall 4: Reject must now write `status='rejected'`, not leave `verified=FALSE`
**What goes wrong:** Today `reject_tournament_completion` calls `_set_verified(..., verified=False)` (service 793-800) which sets `verified=FALSE` — indistinguishable from pending (the whole D-08 problem). If the migration adds `status` but reject still only touches `verified` (now a generated column — which is **not writable**), reject silently does nothing to drain state.
**How to avoid:** `set_tournament_verified` (repo 1487) must be rewritten to write `status` (`'verified'`/`'rejected'`) instead of `verified` (which becomes generated/read-only). The `verified IS DISTINCT FROM $2` no-op guard (repo 1518) becomes `status IS DISTINCT FROM $2`. The service's terminal guard (`if not verified and existing["verified"]` → `AlreadyVerifiedError`, service 842) becomes `if target=='rejected' and existing['status']=='verified'`. The verify no-op short-circuit (service 853) becomes `if target=='verified' and existing['status']=='verified'`.
**Warning signs:** Drain never detected because rejected runs still counted as pending; OR an error writing to a generated `verified` column (`cannot insert into column "verified"`).

### Pitfall 5: Stacked editions (CONTEXT edge case)
**What goes wrong:** With no time cap, if edition N stays stuck and N+1 ends, both sit `awaiting_results`. The poller loop must handle multiple `awaiting_results` editions.
**How to avoid (recommended):** Each edition publishes independently when ITS OWN queue drains (results may post out of order — CONTEXT says acceptable). The poller iterates `WHERE status='awaiting_results' ORDER BY ends_at ASC` and processes each. Champion role: the most-recently-published results win the role (the strip-all-then-grant is naturally last-writer-wins). Planner to confirm vs. gating N+1 behind N (CONTEXT leaves this open; independent is recommended in `<deferred>`).

### Pitfall 6: Empty / all-rejected edition still publishes (CONTEXT edge case)
**What goes wrong:** If every run is rejected (or none submitted), `inflight=0` immediately/eventually and results must still publish a "no-winner" card with NO champion transfer.
**How to avoid:** `fetch_leaderboard` returns `[]` for an empty cycle; `winner_user_id` is `None`; `_transfer_champion_role` already leaves the role vacant when `winner_user_id is None` (bot 543-546). The card already renders "No submissions" (bot 386). This works with no special-casing — but a test must assert the results event still fires with empty standings.

### Pitfall 7: pg_cron unavailable in test DBs
**What goes wrong:** Tests use pytest-databases[postgres] without pg_cron; the cron DO block (0024:400-417) guards on `pg_extension` and no-ops. But the new migration's `process_edition_transitions()` rewrite is a plain `CREATE OR REPLACE FUNCTION` (no extension) — it WILL run in tests, and tests can invoke it directly via `SELECT tournaments.process_edition_transitions()`.
**How to avoid:** Migration tests call the function directly to assert the timing-only flip (edition → `awaiting_results`, cycles → `finalizing`, N+1 created, NO outbox row written). Keep the cron-scheduling DO block guarded exactly as 0024 does.

async def count_inflight_verifications(self, edition_id: int, *, conn: Connection | None = None) -> int:
    """Count completions still pending verification across an edition's child cycles."""
    _conn = self._get_connection(conn)
    return await _conn.fetchval(
        """
        SELECT COUNT(*)
        FROM tournaments.completions tc
        JOIN tournaments.cycles cy ON cy.id = tc.cycle_id
        WHERE cy.edition_id = $1 AND tc.status = 'pending'
        """,
        edition_id,
    )

## Project Constraints (from CLAUDE.md)

- **No ORM** — raw AsyncPG SQL with `$1,$2` positional params, CTEs for complex queries. All new repo methods follow this.
- **Bot NEVER writes Postgres** — force-publish from the bot goes bot → API route → service → DB. The bot only reads via API (`get_tournament_category`) and consumes events.
- **pg_cron owns scheduled timing** — but D-06 moves outcome computation OUT of cron into the poller. Cron stays timing-only.
- **`BaseService.publish_message` requires an idempotency key** unless the routing key is in `IGNORE_IDEMPOTENCY` (`di/base.py`). New `api.tournament.results` event uses `tournament:results:{edition_id}`.

- **DB exception handling** — catch `UniqueConstraintViolationError`/`ForeignKeyViolationError`/`CheckConstraintViolationError` from `repository.exceptions`, transform to `CustomHTTPException` only where a user-friendly message is needed; let unexpected errors propagate.
