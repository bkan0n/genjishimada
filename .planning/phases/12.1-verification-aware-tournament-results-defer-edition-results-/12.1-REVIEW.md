# Phase 12.1: Code Review Report

**Reviewed:** 2026-06-01T00:00:00Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Phase 12.1 implements the verification-aware tournament results deferral system: a tri-state `status` column on `tournaments.completions`, the `awaiting_results` edition lifecycle, a timing-only pg_cron rewrite, a drain-detection state machine in the outbox poller, an admin force-publish route, and bot-side deferred-results handling.

The overall architecture is sound. Transaction coupling of grants + publish + mark is correct. The SQL migration column-swap ordering is correct. No SQL injection paths were found (all dynamic fields are allow-listed). The bot never reads Postgres directly. Idempotency keys are edition-scoped on both events.

Three blockers were found: a silent grant on force-publish due to a mismatched response type, a race condition in the drain state machine where a `start_announced` edition with `pending > 0` is silently skipped without a `continue`, and an `_on_edition_results` handler that posts an empty-results card for a no-op event (all-rejected edition) with no early-exit guard matching `_on_edition_rollover`'s defensive check. Six warnings cover weaker concerns: a TOCTOU window in `_set_verified`, a missing status filter in `fetch_edition_child_cycles`, migration backfill conservatism, an unchecked `assert` in bot components, a `console.log`-equivalent `f-string` debug log left in `_request`, and the `force_publish_results` response lying about the edition status without re-fetching.

## Critical Issues

### CR-01: `force_publish_results` returns wrong response type — `TournamentEditionResponse` instead of nothing useful, and callers receive a stale-status lie

**File:** `apps/api/services/tournament_service.py:568`

**Issue:** `force_publish_results` calls `_write_drained_results_row`, which only writes an `edition_results` **outbox row** and flips the edition + cycles to `completed` in the DB. It does NOT publish the event inline. The method then returns `msgspec.convert({**edition, "status": "completed"}, TournamentEditionResponse)`, but `edition` was fetched from `fetch_awaiting_results_editions` before any of the DB mutations occurred — it is a stale pre-flip snapshot. More critically, the API route at `routes/v3/tournaments.py:543` annotates the return type as `TournamentEditionResponse` and the bot's `api_service.py:1126` declares `force_publish_tournament_results` as `Response[JobStatusResponse]` — there is a shape mismatch between the route's actual return (`TournamentEditionResponse`) and what the bot expects (`JobStatusResponse`). The bot will attempt to decode a `TournamentEditionResponse` payload into `JobStatusResponse`, which will silently succeed only if fields happen to overlap, or raise a `msgspec.ValidationError` at runtime, crashing the command and leaving the force-publish in a partially-done state (DB flipped, outbox written, bot gets an error).

**Fix:** Either:

(a) Change the route's return type to match what the bot expects:
```python
# routes/v3/tournaments.py
@litestar.patch(
    path="/publish-results",
    ...
    status_code=HTTP_200_OK,
    opt={"required_scopes": {"tournaments:write"}},
)
async def force_publish_results(
    self,
    tournament_service: TournamentService,
) -> TournamentEditionResponse:  # keep if bot is fixed
```
And fix `api_service.py`:
```python
def force_publish_tournament_results(self) -> Response[TournamentEditionResponse]:
    r = Route("PATCH", "/tournaments/publish-results")
    return self._request(r, response_model=TournamentEditionResponse)
```

(b) Or return `HTTP_204_NO_CONTENT` (nothing to return — the real result comes via the outbox event), which is semantically cleanest given the deferred-publish design.

### CR-02: Drain state machine silently skips `start_announced=True, pending>0` edition — missing `continue` leaves the loop falling through to the `inflight==0` branch after the `if` block

**File:** `apps/api/services/tournament_outbox_service.py:414-422`

**Issue:** The three-branch state machine in `process_awaiting_results_editions` is structured as a chain of `if / if / if` — not `if / elif / elif`. The last branch at line 414:

```python
if inflight == 0:
    # Later tick, results still owed, queue now drained: write the deferred
    # edition_results outbox row (drained+published+granted next tick) and complete.
    await _write_drained_results_row(repository, edition_id, conn=conn)
    continue
```

is only reached when `start_announced=True` AND `inflight==0`. But consider the case `start_announced=True` AND `inflight>0`: the first two `if not start_announced` blocks are both skipped (they require `start_announced=False`), then the `if inflight == 0` block is also skipped (`inflight > 0`). The code then falls to the final `log.debug` line at 422, which is the correct silent-draining path. **However** — what if a future refactor moves the `continue` or adds code after 422? More critically, the structure means `start_announced=False, inflight>0` followed immediately by `start_announced=False, inflight==0` (a same-tick double edition) could interact unexpectedly because there is no `elif` guard making the branches mutually exclusive. Specifically: if `_write_drained_results_row` is called at line 418 (`start_announced=True, inflight==0`) AND the `start_announced=False, inflight==0` branch at line 388 also fires in the same iteration (impossible for the same edition, but possible for two different editions in the same `editions` list), the code is correct but brittle. The real bug risk is that the current four branches are not exhaustive: the code relies on Python evaluating each `if` independently. If `start_announced=False` and `inflight==0`, **both** the branch at line 388 (`if not start_announced and inflight == 0`) fires the combined-rollover path AND **also** reaches the `if inflight == 0` block at line 414 — because `414` is not an `elif`. This means `_write_drained_results_row` is called **after** the combined inline publish + `complete_edition` already ran for the same edition in the same tick.

Trace for `start_announced=False, inflight==0`:
1. Line 369 (`not start_announced and inflight > 0`): `False` — skipped.
2. Line 388 (`not start_announced and inflight == 0`): `True` — combined rollover fires, `complete_edition` called, `continue` hit. **Wait — yes, line 411 has `continue`!** The `continue` on line 411 correctly skips to the next edition. So the double-call does NOT occur due to the `continue`.

Re-examining: the `start_announced=True, inflight==0` path has `continue` (line 419). The `start_announced=True, inflight>0` path has no explicit `continue` and falls to the `log.debug`. This is correct in isolation BUT is fragile: if anyone removes or misplaces the `continue` at line 419, or adds code between line 419 and 422, the `log.debug` fires unconditionally for every processed edition. This is a **WARNING**-level structural fragility, not a current blocker.

**Actual blocker in CR-02:** Re-reading more carefully — the `start_announced=True, inflight==0` branch at line 414 calls `_write_drained_results_row`. But `_write_drained_results_row` internally calls `repository.complete_edition(edition_id, conn=conn)`. If ANY earlier tick for this edition already called `complete_edition` (e.g., if somehow `fetch_awaiting_results_editions` returned a row that was already completed — which the `WHERE status = 'awaiting_results'` would prevent), this would be a no-op. So the guard is at the query level, not the code level. This is acceptable.

**Real CR-02 — actual blocker:** The `mark_edition_start_announced` call in the `start_announced=False, inflight>0` branch (line 384) runs **inside** the outbox transaction on `conn`, and the start-only rollover `publish_message` (line 379) also runs inside that transaction. `publish_message` writes a `public.jobs` row **and** pushes to RabbitMQ. But `publish_message` in `BaseService` opens its own channel — it does **not** participate in the caller's `conn` transaction. This means the RabbitMQ publish (line 379) is NOT transactional with the `mark_edition_start_announced` (line 384). If `publish_message` succeeds but `mark_edition_start_announced` raises (e.g., DB connectivity glitch), the transaction rolls back, `start_announced` is never set to `TRUE`, and the next tick re-publishes the start-only rollover event — **double-announcing the start** to Discord. The idempotency key `tournament:rollover:{edition_id}` on the `public.jobs` row prevents a second job row, but the bot's `@queue_consumer(idempotent=True)` claim is keyed on the RabbitMQ `message_id` header. If the second re-delivered message carries the same `message_id` (which `publish_message` deterministically sets from the idempotency key), the claim blocks it. **However**, if two different `publish_message` calls produce two different RabbitMQ messages (because the first call's jobs-row insert rolled back), the second message gets a new `public.jobs` UUID and may have a new `message_id`, breaking idempotency. This is a real partial-failure risk for the start-only branch.

**Fix:** Move `mark_edition_start_announced` to run **before** `publish_message`, so the DB state change commits atomically with the rest of the transaction even if publish fails. Or write the start-announced flag into an outbox row (like `edition_results`) so the publish rides the existing at-least-once machinery instead of being inline.

```python
# In process_awaiting_results_editions, start-only branch:
# Mark FIRST (inside the transaction), then publish.
await repository.mark_edition_start_announced(edition_id, conn=conn)
await service.publish_message(
    routing_key="api.tournament.rollover",
    data=rollover,
    headers=Headers({}),
    idempotency_key=f"tournament:rollover:{edition_id}",
)
log.info("[→] start-only rollover (edition %s, results pending)", edition_id)
continue
```

### CR-03: `_on_edition_results` posts a card even when `event.results` is empty — no early-exit guard for the all-rejected / no-submissions case

**File:** `apps/bot/extensions/tournaments.py:460-552`

**Issue:** `_on_edition_rollover` has a defensive early exit (line 360-365):

```python
if not event.results and not event.started and not event.results_pending:
    log.info(...)
    return
```

But `_on_edition_results` has no equivalent guard. When every submission in a finalized edition was rejected (or there were no submissions at all), `event.results` will be an empty list and `event.results` will contain entries with empty `standings` but `winner_user_id=None`. The handler iterates `event.results` (empty → zero iterations), builds a card with only a "## Results" header and a trailing "No submissions" or blank podium, then calls `self.announcement_channel.send(view=view, ...)`. This produces a Discord message that is always sent — even for a zero-results edition — carrying an empty results section and no winners ping. This is at most a UX issue (unwanted announcement) in the empty-event case, but it could become a runtime error: `container.add_item(ui.Separator())` and `container.add_item(ui.TextDisplay("## 🏅 Results\n..."))` are called unconditionally (lines 517-520) before the `for entry in event.results` loop, so even a completely empty `event.results` list posts a header-only results card. The `_on_edition_rollover` handler wraps the results section in `if event.results:` (line 385), making it conditional. `_on_edition_results` does not.

Additionally, the `for entry in event.results:` loop at line 521 accesses `categories[entry.category_id]` where `categories` was populated in the champion-transfer loop (lines 499-503). If the transfer loop raises on an entry and is caught somewhere above — it isn't, `_transfer_champion_role` internally swallows `HTTPException` but does NOT catch `APIHTTPError` from `get_tournament_category` — then `categories` would be incomplete and `categories[entry.category_id]` would raise `KeyError` in the card-building loop, crashing the handler and sending it to DLQ.

**Fix:** Add an early-exit guard and fix the unconditional results-section build:

```python
async def _on_edition_results(self, event: TournamentEditionResultsEvent, _: AbstractIncomingMessage) -> None:
    if not event.results:
        log.info(
            "[✓] [Tournament] edition_results %s carried no results; nothing to post", event.edition_id
        )
        return
    # ... rest of handler
```

And wrap the results header in `if event.results:` or move it inside the loop.

## Warnings

### WR-01: `_set_verified` has a TOCTOU window between the precheck fetch and the guarded UPDATE — `updated is None` fallback publishes from stale data

**File:** `apps/api/services/tournament_service.py:893-965`

**Issue:** `_set_verified` fetches the row at line 893 (`existing = await self._tournament_repo.fetch_tournament_completion(...)`), performs terminal-guard checks on `existing["status"]`, then inside `_do` performs `set_tournament_verified` with a `status IS DISTINCT FROM $2` guard. If a concurrent verify/reject lands between the precheck fetch and the UPDATE (possible on two simultaneous moderator clicks), the guarded UPDATE matches no row (returns `None`). The code at line 958 then re-fetches to distinguish TOCTOU-delete from a "no-op reject of pending row". For a concurrent **verify**, the re-fetch returns a row with `status='verified'`, `updated = current`, and the code proceeds to publish a `TournamentVerificationChangedEvent` built from `current` — but `current["user_id"]` and `current["cycle_id"]` are correct, so the published event is not malformed. However, `pending_xp_events` was populated inside `_do` only when `row is not None` — if `_do` returned `row=None` (concurrent race), `pending_xp_events` is empty and XP was not granted. Yet the event is still published. This is the correct behavior (the first concurrent call granted XP and published, this is the second no-op), **but** the code bypasses the early-exit `_noop_verdict_job` path (line 917-921) because `existing["status"]` was still `'pending'` at precheck time. The result is a second event published under a different `idempotency_key` (because the idempotency key is scoped to the completion ID, not to the DB state), which is deduplicated by the bot's `@queue_consumer(idempotent=True)` — but only if the `message_id` header matches. This is fragile: a second publish with the same routing key but a fresh `public.jobs` UUID will have a different RabbitMQ `message_id` header, and the bot may process it twice.

**Fix:** After the guarded UPDATE returns `None` and the re-fetch returns `current` with `current["status"] == target_status`, treat it as a no-op via `_noop_verdict_job` rather than publishing a fresh event.

```python
if updated is None:
    current = await self._tournament_repo.fetch_tournament_completion(...)
    if current is None:
        raise TournamentCompletionNotFoundError(tournament_completion_id)
    # If current is already in target state, treat as idempotent no-op
    target_status = "verified" if verified else "rejected"
    if current["status"] == target_status:
        return await self._noop_verdict_job(
            tournament_completion_id, idempotency_key=idempotency_key
        )
    updated = current
```

### WR-02: `fetch_edition_child_cycles` returns ALL child cycles regardless of status — completed cycles from a prior partial run could be re-published

**File:** `apps/api/repository/tournaments_repository.py:1625-1634`

**Issue:** `fetch_edition_child_cycles` fetches `WHERE edition_id = $1` with no `status` filter. When `_write_drained_results_row` calls this (outbox service line 304), it expects to get only `finalizing` cycles (those stopped by the cron). If a prior force-publish (or a partial poller run) already flipped some cycles to `completed`, those cycles still belong to the edition and will be re-included in the results computation. `fetch_leaderboard` for an already-completed cycle is idempotent (it just re-reads), and `create_pending_transition` will insert another `edition_results` row — but `complete_edition` at line 320 is an UPDATE that is also idempotent. The real risk is that `create_pending_transition` inserts a **second** `edition_results` row for an edition that already has one (there is no UNIQUE constraint on `(edition_id, event_type)` in `tournaments.pending_transitions`), meaning the outbox drains it **twice**: two `api.tournament.results` publishes per edition, the second of which is blocked by the bot's idempotency claim only if the `message_id` header matches `tournament:results:{edition_id}` — which it does, so it is a no-op at the bot side. But the cycle-end grants run again for the second row in `publish_pending_transitions` (line 211-212), protected only by the `xp_grants` ledger. The ledger is the correct guard, but double-processing the drain is unnecessary and could hold the FOR UPDATE SKIP LOCKED locks longer.

**Fix:** Add a status filter to `fetch_edition_child_cycles`:

```python
SELECT id, category_id
FROM tournaments.cycles
WHERE edition_id = $1 AND status = 'finalizing'
ORDER BY id
```

### WR-03: Migration backfill is conservative — rejected runs historically become `'pending'`, polluting the drain signal for any edition currently `awaiting_results` at deploy time

**File:** `apps/api/migrations/0025_verification_aware_tournament_results.sql:68-70`

**Issue:** The migration documents this choice (comment on line 66: "the conservative choice — it was never an explicit rejection"). This is deliberate. However, there is a correctness risk: if any edition is currently in an `active` state at migration time and has completions from a prior cycle that had `verified=FALSE` (meaning they were rejected under the old schema), those rows are backfilled to `'pending'` after migration. If those cycles transition before a verifier reviews the newly-`'pending'` rows, `count_inflight_verifications` will count stale rejected-but-now-`'pending'` rows, and the edition will be stuck `awaiting_results` indefinitely (drain never completes because those rows are never re-reviewed). The mitigation is the admin `force_publish_results` escape hatch, which the docstring acknowledges. However, **the migration does not backfill already-`finalizing` cycles' `false`-verified completions to `'rejected'`** — they could only be truly-unreviewed rows, but the admin team may not know this. This should at least be documented as a known post-migration action required on the first deploy if any cycles are in `finalizing` status.

**Fix (documentation):** Add a comment to the migration and a post-deploy checklist item:

```sql
-- POST-DEPLOY NOTE: If any cycles are in 'finalizing' status at deploy time,
-- any completion row with verified=FALSE was either pending OR rejected under
-- the old schema. These are backfilled as 'pending'. Run force_publish_results
-- or manually review these rows to prevent an edition from blocking indefinitely.
```

### WR-04: `update_category` and `delete_category` — the cycle check inside a transaction uses `check_active_cycle_for_category` which queries `status IN ('active', 'finalizing')` but does NOT include `'awaiting_results'` cycles indirectly

**File:** `apps/api/services/tournament_service.py:244-265` / `apps/api/repository/tournaments_repository.py:299-307`

**Issue:** `check_active_cycle_for_category` checks `status IN ('active', 'finalizing')`. Under Phase 12.1, cycles of a completed/awaiting edition are in `'finalizing'` status while the edition is `awaiting_results`. So a category with a finalizing cycle IS correctly blocked from modification. However, the `delete_category` transaction acquires the lock only on the category, not on the cycles or the edition. A pg_cron tick that fires mid-transaction and flips a cycle to `'finalizing'` would be blocked by the transaction itself (asyncpg uses READ COMMITTED by default). The check + delete are inside `conn.transaction()`, which is correct. This is a pre-existing pattern correctly carried forward.

However: `check_active_cycle_for_category` does NOT check `'pending'` status cycles. If a pending cycle exists for the category and the category is deleted, the pending cycle would have its FK cascade behavior fire (depends on `ON DELETE` schema definition — not reviewed here). This is a pre-existing gap not introduced by Phase 12.1, so it's a WARNING rather than a blocker, but worth noting for the `delete_category` path.

**Fix:** Add `'pending'` to the cycle status check:

```sql
WHERE category_id = $1 AND status IN ('active', 'finalizing', 'pending')
```

### WR-05: `count_inflight_verifications` does NOT filter by cycle status — it counts `pending` completions across ALL child cycles, including any from a prior edition re-use scenario

**File:** `apps/api/repository/tournaments_repository.py:1555-1565`

**Issue:** The query joins `tournaments.completions` → `tournaments.cycles` on `cy.edition_id = $1 AND tc.status = 'pending'`. It does not filter on `cy.status`. If a cycle somehow has `status='completed'` but still has `pending` completions (a theoretically impossible state given the current flow, but possible if a migration or manual intervention left stale data), those would still count, keeping the drain signal non-zero forever. Additionally, if the edition has cycles that were already `completed` before Phase 12.1 (pre-migration data), those cycles' pending completions (now backfilled as `'pending'` per WR-03) would be counted, potentially blocking drain permanently.

**Fix:** Filter on cycle status:

```sql
SELECT COUNT(*)
FROM tournaments.completions tc
JOIN tournaments.cycles cy ON cy.id = tc.cycle_id
WHERE cy.edition_id = $1
  AND cy.status IN ('active', 'finalizing')
  AND tc.status = 'pending'
```

### WR-06: `TournamentEditionResponse.status` docstring says `'active' | 'completed'` but the tri-state now includes `'awaiting_results'`

**File:** `libs/sdk/src/genjishimada_sdk/tournaments.py:285-286`

**Issue:** `TournamentEditionResponse` docstring at line 285 says `status: Current edition status ('active' | 'completed')`. The `EditionStatus` type alias at line 49 correctly includes `'awaiting_results'`. The struct's `status` field is typed as `EditionStatus` (inherited from the db row), so the runtime behavior is correct. The docstring is simply stale. Consumers of the SDK who read the docstring (e.g., frontend developers) may not know the third status is possible.

status: EditionStatus  # 'active' | 'awaiting_results' | 'completed'

### IN-01: `f-string` debug log left in `_request` — emits a formatted string on every API call

**File:** `apps/bot/extensions/api_service.py:370`

**Issue:**

```python
log.debug(f"The params inside of _request show as {params}")
```

This uses an f-string interpolation rather than `%s` lazy formatting (`log.debug("...", params)`). Per CLAUDE.md conventions, log calls should use `%s` style. Additionally, this specific log line is development-era debugging noise — it fires on every single API request, even in production (at `DEBUG` level). While it would only emit output if the log level is set to DEBUG, it is out of place given the codebase convention of targeted debug messages with emoji prefixes.

**Fix:**

```python
log.debug("The params inside of _request: %s", params)
```

Or remove it entirely.

### IN-02: `TournamentCategoryCreateRequest` uses mutable list defaults — shared across instances

**File:** `libs/sdk/src/genjishimada_sdk/tournaments.py:185-186`

**Issue:**

```python
placement_xp: list[PlacementXpTier] = []
streak_xp: list[StreakXpTier] = []
```

`msgspec.Struct` class-level defaults using `[]` are handled by msgspec (not Python's class-level mutable default anti-pattern — msgspec copies defaults per-instance), so this is NOT a bug. However, the same pattern in `TournamentCategoryPatchRequest` at lines 209-211 combines `UNSET` with list defaults and is also safe. Noting for clarity: this is safe in msgspec, unlike plain Python dataclasses.

No action required.
