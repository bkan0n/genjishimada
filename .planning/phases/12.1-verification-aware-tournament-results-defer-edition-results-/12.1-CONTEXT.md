# Phase 12.1: Verification-aware tournament results - Context

**Gathered:** 2026-06-01
**Status:** Ready for planning
**Type:** Inserted (urgent) — amends Phase 12 (D-09/D-10/D-11)

<domain>
## Phase Boundary

Phase 12 collapsed the tournament start + end announcements into ONE combined
`edition_rollover` message. The pg_cron `process_edition_transitions()` function
(`apps/api/migrations/0024_tournament_editions_overhaul.sql:238-307`) **snapshots
each category's leaderboard** via `fetch_leaderboard` (`verified DESC, time ASC`)
**at the instant the cron fires**, freezes it into the `edition_rollover` outbox
payload, and the poller grants placement/streak XP and (bot-side) transfers the
champion role from that frozen snapshot.

**The bug:** a tournament run still *pending verification* at the grid boundary is
excluded from standings, placement XP, AND the champion-role transfer. Once the
results are announced they are final — so a run that verifies minutes later (a mod
accepting a video, OCR completing) never counts, and the wrong player can receive
placement XP and the champion role.

This phase decouples edition N's **results** from the on-time **start** of edition
N+1, gating the results on verification draining.

**In scope:**
1. Two announcement states — combined (no pending) vs. start + "results pending"
   placeholder followed by a separate deferred results message (pending exists).
2. Drain-only trigger: deferred results publish the instant the LAST in-flight
   verification for the edition resolves; no time cap.
3. Tri-state verification model so "drained" is detectable.
4. Move results computation + reward grants out of pg_cron into the outbox poller
   (cron becomes timing-only).
5. Champion role held through the pending window; transferred when results settle.
6. Admin force-publish escape hatch for a stuck queue.
7. SDK event(s), bot handler(s), migration(s), service/repo/route changes, tests.

**Out of scope (not this phase):**
- Changing the leaderboard *ranking* formula (tier-then-time, Phase 6) — unchanged;
  `verified` runs still rank above unverified.
- Changing grid timing / drift fix (D-06/D-07/D-08 from Phase 12) — preserved.
- Changing how cycles/editions are selected or transitioned beyond moving results
  computation off the cron.
- Bot writing to Postgres (architecturally forbidden — bot calls API / consumes
  events).
- A time-based grace window / auto-publish deadline (explicitly rejected — D-02).

**Decisions amended from Phase 12:** D-09/D-10/D-11 (one combined message produced
by a single cron-written outbox row) are superseded — the combined message is now
only the *no-pending* case, and results computation/reward grants move from the
cron + poller-from-snapshot to the poller-computes model below.
</domain>

<decisions>
## Implementation Decisions (locked this discussion — do not revisit)

### Announcement state machine
- **D-01:** The **start of edition N+1 always fires on time** (Phase 12 D-12
  unchanged). Only edition N's **results** are gated on verification. The four
  cases:
  - Normal rollover, **no in-flight verifications** → ONE combined message
    (results N + start N+1), exactly as Phase 12 today.
  - Normal rollover, **in-flight verifications exist** → start(N+1) + a "results
    pending verification…" placeholder now; a SEPARATE results(N) message later.
  - Hiatus (paused) + no pending → results-only(N).
  - Hiatus (paused) + pending → "results pending…" placeholder now; separate
    results-only(N) later. Resume-from-hiatus is start-only (no results owed).

### Wait bound
- **D-02:** **Drain-only, no time cap.** Deferred results publish the instant the
  LAST in-flight verification on the edition's child cycles resolves (verified or
  rejected). No grace window / deadline auto-publish. (Rejected: time-cap and
  fixed-grace-window alternatives.)

### Escape hatch
- **D-03:** An **admin force-publish command** (e.g. `/tournament publish-results`,
  edition-scoped to the edition currently `awaiting_results`) publishes the results
  immediately using whatever is currently verified, **abandoning** still-pending
  runs. This is the only escape for a forgotten/stuck verification under D-02.

### Deferred message behavior
- **D-04:** When results are deferred, publish them as a **new separate
  announcement** when the queue drains. Leave the original "pending" placeholder
  as-is (do NOT edit it in place, do NOT store/edit message IDs).

### Champion role
- **D-05:** While edition N's results are deferred, the **previous champion keeps
  the role** through the pending window. The role transfers only when the deferred
  results publish. No role-less gap, no strip-then-regrant churn.

### Architecture — cron timing-only, poller owns results
- **D-06:** **pg_cron `process_edition_transitions()` becomes timing-only.** It
  flips edition N → new status `awaiting_results`, sets child cycles → `finalizing`
  (the status that already exists in the cycle CHECK enum for exactly this), creates
  edition N+1 grid-anchored, pre-rolls N+1's child cycles. It **no longer snapshots
  results, writes the rollover payload, or drives reward grants.** This reinforces
  Phase 12 D-08 (cron only touches grid timing/status, never computes outcomes).
- **D-07:** **The existing outbox poller (`tournament_outbox_poller`, ~10s) owns
  results.** For each edition in `awaiting_results` it counts in-flight
  verifications on its `finalizing` child cycles and:
  - *First tick after rollover, in-flight = 0* → compute results, grant
    placement/streak XP, transfer champion role, emit ONE combined
    `edition_rollover` event, flip edition + cycles → `completed`. (Combined message
    preserved; results already aren't instant today — the cron writes an outbox row
    the ~10s poller publishes — so moving computation to the poller adds no
    meaningful latency.)
  - *First tick, in-flight > 0* → emit a **start-only** event (carrying a
    `results_pending` flag), mark start announced, leave the edition
    `awaiting_results`; champion role held.
  - *Later tick, results still owed, in-flight now = 0* (drained) → compute results,
    grant rewards, transfer champion role, emit a **`edition_results`** (results-
    only) event, flip edition + cycles → `completed`.
  Force-publish (D-03) triggers the drain branch ignoring remaining in-flight.

### Verification state model
- **D-08:** **Tri-state verification** required. A rejected non-PB tournament
  completion currently leaves the row `verified = FALSE`
  (`apps/api/services/tournament_service.py:768-796`), **indistinguishable** from an
  un-reviewed pending run — so "queue drained" is undetectable by counting
  `verified = FALSE`. Add a tri-state (`pending` / `verified` / `rejected`) on
  `tournaments.completions` (or an equivalent `resolved` marker / per-cycle in-flight
  counter). Leaderboard ranking is unchanged: `verified` still ranks above
  not-verified; `pending` and `rejected` both sort below.

### SDK / events
- **D-09:** A **new results-only event** (e.g. `TournamentEditionResultsEvent`,
  routing `api.tournament.results`, idempotency key
  `tournament:results:{edition_id}`). `TournamentRolloverEvent` gains a
  `results_pending: bool` and its `results` becomes optional/empty in the deferred
  case. Bot adds a `_on_edition_results` handler that posts the deferred results as
  a new message and performs the held champion-role transfer; `_on_edition_rollover`
  renders start + (results | "pending" placeholder).

### Claude's Discretion (defer to research/planning)
- Exact tri-state representation: status enum on `tournaments.completions` vs.
  `rejected boolean` vs. a per-cycle in-flight counter; and the migration number
  (next sequential after 0024).
- Exact names/shapes of the new event + the `results_pending` field; whether the
  combined no-pending case keeps `TournamentRolloverEvent` carrying results or also
  routes through the results event.
- Where the in-flight count query lives (new repo method vs. extend existing) and
  how the poller distinguishes "first tick / start not yet announced" from "results
  still owed" (e.g. a `start_announced` marker on the edition, or deriving it from
  status + an outbox/announcement record).
- Whether results computation in Python reuses `fetch_leaderboard` + the existing
  `award_cycle_end` / `_reset_non_participant_streaks` reward path verbatim (likely
  yes — feed it freshly-computed entries instead of the cron snapshot payload).
- Force-publish command surface (slash command name, scope guard, confirmation).

### Edge cases to spec
- **Stacked editions:** with no cap (D-02), if N's results stay stuck and N+1 ends,
  both sit `awaiting_results`. Recommendation: each publishes independently when its
  own queue drains (results may post out of order — acceptable). Planner to confirm
  vs. gating N+1 behind N.
- **All runs rejected / empty edition** → results still publish (no-winner card),
  no champion transfer.
- **Force-publish before rollover** (no `awaiting_results` edition) → no-op / clear
  error.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- The outbox → RabbitMQ poller (`publish_pending_transitions` + the `app.py`
  lifespan) — extend its loop to compute results for `awaiting_results` editions;
  keep the transactional publish-before-mark + per-cycle reward grant pattern.
- `award_cycle_end` + `_reset_non_participant_streaks` reward path — reuse verbatim,
  feeding freshly-computed leaderboard entries instead of the cron snapshot payload.
- The bot's one-combined-LayoutView-card pattern (Phase 12 `_on_edition_rollover`,
  CV2; see memory `cv2-layoutview-no-content` — pings go in a TextDisplay) — the
  results card and the "pending" placeholder reuse it.

### Established Patterns
- Cycle status is a forward-only CHECK enum (`pending → active → finalizing →
  completed`); `finalizing` is the natural "ended, not final" state for the pending
  window.
- Transition work lives in PL/pgSQL invoked by pg_cron (DB owns scheduled timing) —
  but outcome computation is moving to the API poller (D-06/D-07).
- jsonb outbox payloads round-trip through msgspec via `_async_pg_init` codecs; a
  payload/struct key drift surfaces as a `msgspec.convert` error (kept unpublished).
- Idempotency keys are edition-scoped (`tournament:rollover:{edition_id}`); the new
  results event uses `tournament:results:{edition_id}`.

### Integration Points
- New migration (next after 0024): `awaiting_results` edition status; tri-state
  verification on `tournaments.completions`; rewrite `process_edition_transitions()`
  to timing-only.
- Outbox poller: drain detection + results computation + reward grants + two emit
  paths (combined vs. start-only vs. results-only).
- SDK: results-only event + `results_pending` flag.
- API routes/service: force-publish endpoint/command; verify/reject updates the
  tri-state.
- Bot: `_on_edition_results` handler + "pending" placeholder rendering.
</code_context>
