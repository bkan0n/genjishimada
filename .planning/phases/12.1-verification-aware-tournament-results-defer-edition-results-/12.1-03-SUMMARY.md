# Phase 12.1 Plan 03: Repository + service verify/reject tri-state writes Summary

**Rewires the verify/reject write-path and the drain-signal query to the new tri-state (D-08): `set_tournament_verified` now writes `status` ('verified'/'rejected') instead of the now-generated read-only `verified` column, adds `count_inflight_verifications(edition_id)` for the poller's drain detection, and rewrites the service terminal/no-op guards to read `status` — clearing all 11 verify/reject/leaderboard failures inherited from Wave 1's migration 0025.**

## Accomplishments
- `set_tournament_verified` (repo) rewritten to `SET status = $2 WHERE id = $1 AND status IS DISTINCT FROM $2` (verdict mapped from the bool: True->'verified', False->'rejected'). Writing the generated `verified` column would raise `GeneratedAlwaysError`; the `IS DISTINCT FROM` no-op idempotency guard (CR-01/WR-06) is preserved, now keyed on `status` (T-12.1-05, T-12.1-07).
- `count_inflight_verifications(edition_id)` added — `COUNT(*) FROM tournaments.completions tc JOIN tournaments.cycles cy ON cy.id = tc.cycle_id WHERE cy.edition_id = $1 AND tc.status = 'pending'`. Returns the in-flight count per edition; zero when the queue has drained. This is the drain signal Plan 04's poller consumes (D-08).
- `fetch_tournament_completion` SELECT now returns `status` alongside the generated `verified`, so the service guards read the tri-state source of truth.
- Service `_set_verified` terminal guard rewritten: `if not verified and existing['status'] == 'verified': raise AlreadyVerifiedError` — a verified (possibly already-rewarded) run cannot be reverted (T-12.1-06). No-op short-circuit rewritten: `if verified and existing['status'] == 'verified': return _noop_verdict_job(...)` (T-12.1-07). The atomic `_do(active_conn)` acquire-or-inject transaction wrapper (row flip + participation-XP grant in one transaction) is unchanged.
- The 11 Wave-1-inherited failures (verify/reject/leaderboard/cross-write/fetch-completion) are now GREEN; the only remaining tournament-suite failures are the 3 owned by Plan 04 (`test_edition_transitions.py`) + 1 pre-existing `-n 4` flake.

## Decisions Made
- **Signature:** kept `set_tournament_verified(verified: bool = True)` (the smaller diff, explicitly sanctioned by the plan) and mapped the bool to the `status` string internally. This required ZERO change at the PB-side-effect caller in `completions_service.py:1117` (which relies on the `verified=True` default) — the verify/reject service callers already pass the right bool.
- **No-op event verified field:** derived from `existing['status'] == 'verified'` rather than the generated `verified` mirror, keeping the replayed event consistent with the persisted verdict and matching the mock-based test contract.
- **Fixture backfill rule:** `verified=False -> status='pending'` (a historical FALSE seed was never an explicit rejection — consistent with migration 0025's data backfill, 12.1-01).
