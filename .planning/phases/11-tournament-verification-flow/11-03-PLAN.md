<objective>
Build the non-PB tournament verification surface — the genuinely new construct of the phase. A slower-than-PB run (recorded by 11-02's D-07 relax with NO core row) needs its own verification because it never fires a core verification event. This plan adds:
1. An OCR variant (`attempt_tournament_auto_verify_async`) for no-video runs + its in-process `tournament.ocr.requested` listener, mirroring the completions OCR path but verifying the tournament row instead of a core row (P4).
2. The non-PB dispatch in `submit_completion`'s D-07 branch: no-video → emit tournament OCR event; video → publish `TournamentCompletionCreatedEvent` on `api.tournament.completion.created` for bot mod review (the bot view lands in 11-05).
3. `verify_tournament_completion` / `reject_tournament_completion` service methods + the scoped `PATCH /tournaments/completions/{id}/verify|reject` endpoints the bot calls back (bot never writes the DB).

Purpose: SC-2 — slower-than-PB runs get verified (OCR or mod) and recorded; D-02 first-verified-run auto-enrolls; D-06 participation XP fires on tournament verification, idempotently.
Output: OCR variant + listener + verify/reject service methods + endpoints + tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bot → verify API | the bot Accept/Reject callback crosses into a state-changing endpoint; only authorized verifiers may flip verified |
| OCR HTTP service → API | the external OCR /extract response drives auto-verification; a spoofed/incorrect match would falsely verify |
| API → RabbitMQ | tournament completion-created + verification-changed publishes must be idempotent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-11-10 | Tampering / Replay | duplicate verify → double XP | mitigate | award_participation xp_grants UNIQUE ledger; called unconditionally; verify publish keyed `tournament:verify:{tc_id}`; two-verify test asserts one XP row |
