<objective>
Lay the persistent-state and data-access foundation for the rewards engine: the
double-grant ledger (migration 0022), the SDK XP type member, and the four new
repository methods that the reward service (08-02) and hook wiring (08-03) depend on.

Purpose: Every reward grant in this phase must be idempotent against the Phase-7
outbox's at-least-once re-delivery. The ledger's UNIQUE(cycle_id, user_id, reason)
constraint is the only real double-grant guard because `api.xp.grant` is in
IGNORE_IDEMPOTENCY (queue idempotency is a no-op). This plan also adds the
reset-capable streak update (the existing `upsert_streak` is increment-only and
cannot reset non-participants to 0), the per-cycle participant query that drives
streak recomputation, and the all-tracked-users query that drives the 08-03
non-participant reset sweep.

Output: migration 0022, one-line SDK `XP_TYPES` edit (+ `just fix`), four new
repository methods, and the two Wave-0 test scaffolds so downstream `<verify>`
commands have a target to run.
</objective>
